# 과제1 보고서의 노션 표와 제출 PDF 개선: 이번 세션의 기술 회고

> 작성 기준: 2026-09-26 세션에서 실제로 확인·수정·검증한 내용이다. 이는 작업 회고와 재현 기록이며, 과제 제출용 `과제를하면서느낀점.md`나 학생 본인의 소감을 대신하지 않는다. 사용자가 직접 경험했다고 확인하지 않은 시행착오를 제출 보고서에 옮겨 적어서는 안 된다.

> 이 문서는 표 개선 당시의 기록이다. 아래에서 언급하는 `report_pdf.py`, `notion_table_rows.py`, `notion_table_reflow.py`는 현재 작업 트리에 없으므로 현행 실행 절차로 사용하지 않는다.

## 1. 출발점과 도달한 상태

사용자가 노션에 올린 보고서의 **코드 설명 표가 이상하게 보이는 이유**를 물었다. 첨부 PDF와 노션 페이지, 로컬 보고서 원고, 동기화 스크립트를 함께 확인하면서 두 문제가 구분되었다.

1. **제출용 PDF 문제:** 긴 C 코드가 노션의 좁은 표 셀에 들어간 채 A4 세로 PDF로 출력되었다. 명령문이 자동으로 여러 줄에 접히고, `read_state`처럼 긴 표 행은 다음 페이지로 분할되었다. 설명 셀은 먼저 끝나 다음 페이지의 오른쪽이 비었다.
2. **노션 화면 문제:** 노션 페이지에서도 각 함수의 코드 전체가 표 본문 한 행의 왼쪽 셀에 들어 있었다. 페이지의 `전체 너비`는 이미 켜져 있었지만 표 자체는 페이지 폭을 사용하지 않아 코드가 심하게 접혔다.

## 2. 가장 먼저 바로잡은 판단: 채점 기준이 레이아웃을 결정한다

처음에는 코드를 표 밖의 전체 폭 코드 블록으로 빼고 설명을 아래에 두면 읽기 쉬울 것이라고 생각했다. 하지만 `과제/과제1/과제 채점기준.pdf`를 확인하자, 그 방법은 **제출본의 요구 형식과 충돌**했다. 채점 기준은 페이지를 반으로 나눠 왼쪽에 코드, 오른쪽에 그 코드의 분석을 두고, 함수별로 칸을 구분하라고 한다. 코드 이미지는 인정되지 않고 텍스트여야 한다.

여기서 얻은 교훈은 **가독성 개선책을 결정하기 전에 제출 형식의 강제 조건을 확인해야 한다**는 것이다. 눈에 보기 좋은 일반적인 문서 구조가 이번 과제의 정답은 아니었다. 이후 제출 PDF는 함수별 50:50 구획을 지키고, 노션 화면은 편집 가능한 2열 표를 지키는 두 결과물로 나눠 해결했다.

이 구분 덕분에 두 종류의 성공을 섞어 말하지 않을 수 있었다.

- **노션 화면의 성공:** 셀 내용을 직접 편집하고, 함수의 코드 구간과 관련 설명을 옆에서 읽을 수 있다.
- **제출 PDF의 성공:** A4 페이지에서 코드가 충분히 읽히고, 함수별 좌우 구획과 코드 텍스트 선택·추출이 유지된다.
- **아직 확인하지 않은 것:** 개선 후 노션에서 다시 PDF를 내보냈을 때도 제출 후보 PDF와 같은 페이지 구성이 나오는지. 노션의 연속 페이지와 PDF 내보내기 엔진이 페이지 분할을 결정하므로 동일하다고 주장하지 않는다.

## 3. 원인 분석에서 배운 점: 텍스트 보존과 시각적 품질은 별개다

기존 노션 동기화 흐름의 `table_from_columns()`는 함수별 전체 C 코드를 2열 표의 왼쪽 **하나의 본문 셀**에 담았다. 노션 API 조회에서는 코드와 줄바꿈이 보존되어 있었다. 따라서 문제를 “코드가 사라졌다”라고 진단하면 부정확했다. 실제 문제는 긴 셀의 폭과 인쇄 시 표 행을 나누는 방식이었다.

첨부 PDF의 2~3쪽에서 `read_state` 표가 페이지 경계를 넘었다. 코드 왼쪽은 계속되지만 오른쪽 설명은 먼저 끝나 다음 페이지의 설명 공간이 비었다. 명령문의 원래 줄바꿈 외에 좁은 셀 때문에 시각적 줄바꿈이 추가되어 코드 구조를 파악하기 어려웠다.

따라서 다음 세 층을 따로 검사해야 한다.

| 층 | 확인할 질문 | 이번 세션의 검증 |
|---|---|---|
| 데이터 | 노션 API 셀의 코드·설명 원문이 살아 있는가? | 기존 여섯 함수 셀과 로컬 C 코드 대조 |
| 화면 | 노션에서 열 폭과 행 구분이 읽기 쉬운가? | 노션 데스크톱 앱에서 함수 표 여섯 개를 `너비에 맞추기`로 확장 |
| 제출 파일 | PDF에서 페이지 분할·문자 선택·표 구획이 적합한가? | PDF 전 페이지 렌더링, 텍스트 추출 및 소스 코드 대조 |

같은 원문이 노션 API에서는 정확해도 PDF에서는 읽기 어렵게 보일 수 있다. **동기화 성공을 제출 형식 검증의 대체물로 삼지 않는 것**이 핵심이다.

## 4. 제출 PDF 제작에서 얻은 교훈

### 4.1. 코드 줄을 무조건 줄이지 말고 실제 폭을 측정한다

로컬 `보고서.md`의 여섯 코드 블록을 `HW1.c`와 대조한 뒤 A4 가로의 왼쪽 절반에 실제로 들어가는지 글꼴 폭을 측정했다. 사용한 AppleGothic 8.5pt에서 가장 긴 현재 코드 줄은 약 341pt이고, 코드 칸 안쪽 폭은 약 377pt였다. 그래서 원본 C 코드의 줄바꿈을 다시 쓰거나 글자를 더 작게 만들 필요가 없었다. 더 긴 새 줄이 생기면 밖으로 그리거나 조용히 접지 않고 생성 단계에서 실패하도록 했다.

`read_state`는 54줄이므로 페이지 높이 때문에 구획을 나눴다. 다음 쪽에 `(계속)` 제목과 좌우 칸을 다시 보여, 코드만 홀로 이어지는 상황을 피했다. 짧은 함수는 각각의 좌우 구획 안에 배치했다. 이를 구현한 코드는 `과제/과제1/검토자료/report_pdf.py`다.

### 4.2. 폰트가 등록되었다고 출력이 보이는 것은 아니다

첫 PDF 시안에서 Noto Sans Gothic 글꼴을 ReportLab에 등록했을 때 예외가 없었지만, 렌더링 화면에는 글자가 보이지 않았고 `pdftotext`는 페이지 구분만 추출했다. 한 줄짜리 독립 PDF로 원인을 분리해 AppleGothic은 한글과 영문을 **보이게 렌더링하고 추출도 가능**함을 확인한 뒤 교체했다.

여기서 얻은 교훈은 **폰트 등록 성공, 시각 렌더링 성공, 텍스트 추출 성공을 각각 확인해야 한다**는 것이다. 특히 과제 기준이 복사 가능한 텍스트를 요구하므로, 그림으로 보이는 것만으로도 충분하지 않았다. 반대로 이 글꼴 경로는 macOS에 의존하므로 다른 운영체제에서 재생성할 때는 대체 글꼴 검증이 필요하다.

### 4.3. 페이지 흐름은 제목과 본문을 함께 검사한다

초기 전체 PDF에서는 `3.2`, `3.3` 예제 제목이 페이지 마지막에 남고 입력 블록이 다음 페이지로 넘어가는 경우가 있었다. 제목만 보존하는 테스트는 처음에 이를 잡지 못했다. 제목이 **실제 입력 숫자 블록과 같은 페이지에 있는지** 검사하는 테스트로 고쳐 재현했고, ReportLab의 `keepWithNext` 설정을 적용했다. `3.4` 경계값 표도 제목과 표 머리행이 같은 페이지에 오도록 본문 연결 규칙을 추가했다.

이 과정은 “제목이 PDF에 있다”와 “제목이 읽는 사람에게 올바른 위치에 있다”가 다른 검증이라는 것을 보여준다.

### 4.4. PDF 출력 경로의 내용 누락을 실패로 만든다

최종 PDF 생성기는 `보고서.md`의 기본 정보·함수 분석·실행 예제·요약을 포함한다. 함수 분석에서 예상 밖의 문단이 추가됐는데 파서가 이를 조용히 무시하는 경우, 또는 `read_state` 분석 항목의 개수나 순서가 바뀌어 정해 둔 구획 매핑이 틀리는 경우를 독립 검토에서 발견했다. 각각 실패 테스트를 먼저 만들고, 변경된 입력이면 명시적 오류를 내도록 고쳤다.

노션 최신본과 로컬 원고가 다른데도 PDF를 만들 수 있던 경로도 막았다. 전체 PDF CLI는 노션 스냅샷과 새로 읽은 노션 Markdown을 요구하고, 함수 코드·설명 및 주요 서술이 로컬 원고와 맞는지 검사한다. 이번에 노션 표가 여러 행으로 바뀐 뒤에는 **여러 코드 셀을 순서대로 합치고 설명 항목의 중복·누락을 비교**하도록 이 검사도 확장했다. 행 사이로 설명 항목을 옮긴 것은 허용하지만 항목 자체의 변경은 거부한다.

## 5. 노션의 편집 가능한 표를 바꾸며 얻은 교훈

### 5.1. 노션 표 셀은 코드 블록이 아닌 rich text다

노션 API의 `table_row.cells`는 셀마다 rich text 배열이다. 기존 코드 셀에는 `code: true` 인라인 서식이 붙어 있었다. 이 덕분에 코드는 셀 안에서 편집·복사할 수 있지만, 노션 기본 코드 색상과 좁은 폭의 자동 줄바꿈이 적용된다. 표 셀에 독립된 C 코드 블록을 넣어 제출 PDF와 서체·페이지 분할을 완전히 똑같이 만드는 방식은 사용할 수 없었다.

최종 화면에서는 이 인라인 코드 서식을 유지하고, **긴 코드를 한 셀에 두지 않는 것**과 **표 자체를 페이지 너비에 맞추는 것**으로 해결했다. 코드를 여러 행에 나누었으므로 한 함수 전체를 한 셀에서 한 번에 복사하기는 이전보다 불편할 수 있다. 대신 각 코드 구간과 해당 설명을 같은 행에서 읽고 편집할 수 있다.

### 5.2. 글자 수가 아니라 의미 있는 코드 경계로 행을 나눈다

여섯 함수의 코드 줄 수는 각각 `28, 54, 8, 9, 32, 28`줄이었다. 최종 본문행 수는 `3, 4, 1, 1, 3, 2`개다. 예를 들어 `read_state`는 프로세스·자원 수 검사, Available 입력, Allocation 입력, Maximum 입력 및 모순 검사로 나뉜다. `search_safe_sequence`는 기저 조건, 후보 선택·자원 회수, 백트래킹 복원으로 나뉜다.

분할 위치와 오른쪽 설명 항목 배정은 `과제/과제1/검토자료/notion_table_rows.py`에 명시했다. 코드 조각은 원본의 `splitlines(keepends=True)` 연속 구간으로 만들었다. 그러므로 새 행의 왼쪽 텍스트를 순서대로 이어 붙이면 **원래 노션 코드 셀과 정확히 같은 문자열**이 된다. 오른쪽은 `Counter`로 기존 기능 명세·분석 항목 38개가 각각 정확히 한 번 들어갔는지 확인했다. 문장 자체를 새로 쓰거나 학생의 경험을 만들어 넣지 않았다.

### 5.3. 외부 페이지 교체는 `백업 → 새 표 → 재조회 → 기존 표 보관` 순서가 안전하다

노션 페이지를 한 번에 지우고 다시 만들면 중간 실패 시 원본이 사라질 위험이 있다. `과제/과제1/검토자료/notion_table_reflow.py`는 쓰기 전 블록 트리와 Markdown을 `notion_api/reflow-before-20260926-131222.json/.md`에 저장하고, 함수별 진행 상태를 `reflow-manifest.json`에 기록했다.

각 함수에서 먼저 새 표를 기존 제목 뒤에 추가했다. API에서 새 표를 **다시 읽어** 행 수, 코드 텍스트, 설명 항목, 코드 서식을 확인한 다음에만 이전 표를 노션의 복구 가능한 휴지통으로 옮겼다. 결과 표 네 개의 ID와 내용은 유지됐다. 최종 manifest 상태는 `complete`이며 여섯 함수의 이전·새 표 ID가 기록돼 있다. 액세스 토큰은 환경변수 `NOTION_TOKEN`에서만 읽고 파일에는 저장하지 않았다.

중단 후 다시 실행할 때 새 표를 중복 생성하지 않도록 두 경우를 다뤘다. manifest에 새 ID가 기록된 경우 그 표를 검증해 이어가고, 쓰기 응답 뒤 manifest 기록 전에 중단한 경우에도 제목과 이전 표 사이에 들어간 표를 조회해 재사용한다. `PATCH` 응답이 불확실할 때 무작정 같은 요청을 재시도하지 않는 이유가 여기에 있다.

### 5.4. 모든 입력을 검사한 뒤 첫 번째 쓰기를 시작한다

독립 코드 검토에서 중요한 순서 문제가 발견됐다. 첫 구현은 함수별로 `분할 검증 → 그 함수 교체`를 반복했다. 마지막 함수 `main`에 설명 항목이 하나 더 생기면, 앞의 다섯 표를 이미 교체한 뒤에야 오류를 발견할 수 있었다. 현재 코드는 **여섯 표 모두의 코드 줄·설명 구조·새 payload를 먼저 준비**하고, 하나라도 맞지 않으면 첫 원격 쓰기 전에 실패한다.

또한 중단 후 재개 시 저장된 manifest를 읽는 경로가 현재 `HW1.c`와의 일치 검사를 건너뛰던 문제를 고쳤다. 재개할 때도 저장된 노션 코드와 현재 C 소스를 먼저 비교한다. 결과 표 역시 ID가 같은지만 보지 않고 쓰기 전 스냅샷의 셀 내용과 현재 셀 내용을 비교한다. 이 세 경로에 대해 실패 테스트를 먼저 실행한 뒤 수정을 확인했다.

### 5.5. `전체 너비`와 각 표의 `너비에 맞추기`는 다른 설정이다

노션 데스크톱 앱에서 페이지의 `전체 너비` 설정은 이미 켜져 있었다. 그럼에도 함수 표들은 페이지 일부 폭만 써서 코드가 계속 잘게 접혔다. 표 블록 메뉴의 `너비에 맞추기`를 **여섯 표 각각에 적용**한 뒤 읽기 편한 두 열이 보이는 것을 확인했다. 최종 노션 Markdown에는 여섯 표마다 `<colgroup>` 안에 `<col width="509">`가 두 개씩, 총 12개 나타난다.

즉 **페이지 폭 설정과 개별 표 폭 설정을 혼동하면 화면 문제가 남는다.** API에서 코드가 정확하다는 사실도 표의 화면 폭을 증명하지 않는다. 화면에서 직접 확인해야 한다.

위 결과는 **검증 시점의 상태**다. 노션의 이후 편집이나 다른 컴퓨터에서의 글꼴·인쇄 결과까지 자동으로 보증하지 않는다. PDF 뷰어에서 사람이 마우스로 코드를 선택·복사하는 조작 자체는 별도로 수행하지 않았지만, PDF 텍스트 추출로 코드가 이미지가 아닌 문자열임을 확인했다. 개선된 노션 페이지를 다시 내보낸 PDF가 제출 후보와 동일한지도 확인하지 않았다.

## 7. 다시 같은 작업을 한다면 따를 순서

1. **공식 채점 기준부터 읽는다.** 이번 과제에서는 함수별 좌우 반 페이지와 텍스트 코드가 레이아웃의 강제 조건이다.
2. **어느 결과물을 고칠지 구분한다.** 노션 화면을 읽기 쉽게 만드는 일과 제출 PDF를 조판하는 일은 연결돼 있지만 성공 조건이 다르다.
3. **원본 내용의 기준을 정한다.** 노션에서 직접 편집한 내용은 쓰기 직전에 다시 읽고, 로컬 원고로 조용히 덮어쓰지 않는다.
4. **코드·설명 보존을 기계적으로 증명한다.** 코드 조각의 연결 문자열은 원본과 동일해야 하고, 설명 항목은 중복·누락 없이 한 번씩 있어야 한다.
5. **새 구조를 먼저 만든 뒤 재조회한다.** 쓰기 명령의 성공 응답만으로 완료를 주장하지 않는다. 예상과 다르면 이전 구조를 그대로 둔다.
6. **PDF는 실제로 렌더링해 본다.** 문서 소스와 생성 명령의 성공만으로 글자 표시, 페이지 경계, 복사 가능성을 알 수 없다.
7. **단계별 증거의 범위를 정확히 말한다.** 테스트 통과, API 일치, 화면 확인, PDF 추출, 실제 제출은 서로 다른 사실이다.
