# 과제1: 본인 작성과 이해가 드러나는 결과물의 기준

- 결정일: 2026-09-21
- 상태: 추천안 A — 본인 이해와 직접 작성이 드러나는 기준으로 확정
- 용도: 과제1 코드와 보고서의 자기 점검
- 성격: 공식 채점 기준을 바탕으로 구체화한 보조 기준. 공식 추가 채점표나 AI 탐지 기준이 아님.

## 1. 목표와 정의

목표는 본인이 구현하고, 이해하고, 직접 설명한 결과물을 만드는 것이다.

> 자신이 작성한 코드의 선택 이유를 설명하고, 실제 입력과 상태 변화를 근거로 결과를 설명하며, 설명 전체가 자신의 이해 수준과 일치하는 결과물.

“AI 티가 나지 않는다”라는 인상만으로는 이 목표의 달성 여부를 판단할 수 없다. 문장이 자연스러워도 본인이 작성하지 않았다면 요구를 충족하지 않는다. 코드가 깔끔하거나 설명이 매끄럽다는 이유만으로 AI 결과물이라고 판단할 수도 없다.

## 2. 공식 문서에서 확인한 요구

### HW1.pdf, 19쪽

- 참고는 가능하나 실제 구현은 반드시 본인이 해야 한다.
- 소스 카피 또는 ChatGPT를 사용한 코드 구현 적발 시 0점이라고 명시한다.
- 보고서는 본인이 직접 작성해야 하며 강의노트나 ChatGPT 내용을 붙여 넣으면 안 된다.
- 제공된 코드와 구현한 코드를 모두 분석해야 한다.
- 구현한 함수의 기능 명세와 실행결과 분석이 필요하다.

### 과제 채점기준.pdf, 1쪽

- 코드의 단순한 라인별 설명 나열 대신 기능과 동작 원리를 분석한다.
- 보고서 점수는 소스코드 분석 1.5점, 실행결과 분석 1점, 양식 0.5점이다.
- 페이지를 반으로 나누어 왼쪽에는 코드, 오른쪽에는 분석을 작성하고 함수별로 구분한다.
- 함수 분석은 코드 주석으로 대체할 수 없다.
- 전역변수, 매크로, 구조체 등 코드 앞부분의 정의도 분석해야 한다. 이 부분은 주석으로 대체할 수 있다.

출처 파일: [HW1.pdf](HW1.pdf), [과제 채점기준.pdf](과제%20채점기준.pdf).

두 문서에는 문체로 AI 사용을 판별하는 공식 기준이 제시되어 있지 않다. 이하 내용은 위 요구를 실제 검토에 사용할 수 있도록 해석한 제안이다. 제출 형식 등 전체 요구는 원문도 함께 확인한다.

## 3. 여섯 가지 점검 기준

| 기준 | 보완이 필요한 상태 | 충족한 상태 |
|---|---|---|
| 작성 주체 | 생성된 코드의 이름만 바꾸거나 생성 문장을 바꾸어 제출한다. | 참고한 개념을 바탕으로 직접 구현하고 직접 서술한다. |
| 과제에 대한 구체성 | 어느 재귀 과제에 붙여도 통하는 설명이다. | 이 코드의 depth, finish, available이 맡은 역할을 연결한다. |
| 인과관계 | 반복·덧셈·재귀 호출 등 동작을 나열한다. | 왜 필요한 연산인지, 생략하면 무엇이 틀리는지 설명한다. |
| 코드와 설명의 일치 | 구현하지 않은 처리나 수행하지 않은 검증을 했다고 설명한다. | 실제 조건·반환값·상태 변화와 설명이 일치한다. |
| 결과의 근거 | “정상적으로 실행되었다”로 끝난다. | 해당 입력에서 어떤 순서가 가능하거나 막히는지 설명한다. |
| 이해의 일관성 | 보고서에 쓴 용어와 식을 본인이 풀어 설명하지 못한다. | 작은 입력이나 조건 변경에도 같은 원리로 설명한다. |

작성 주체는 결과물의 겉모양만으로 확정할 수 없다. 나머지 항목 역시 AI 탐지법이 아니라 이해와 분석의 질을 점검하는 기준이다.

## 4. 과제1에 적용하는 핵심 질문

현재 HW1.c의 안전 순서 탐색과 실행 가능성 판단을 기준으로 다음 질문을 사용한다. 코드를 변경하면 질문과 실제 구현의 대응도 다시 확인한다.

| 코드의 요소 | 본인이 설명할 수 있어야 하는 질문 |
|---|---|
| 모든 프로세스를 선택하면 1 반환 | 왜 0이나 프로세스 수가 아니라 1인가? |
| 완료를 가정하면서 allocation을 available에 더함 | 왜 need나 maximum을 더하지 않는가? |
| 재귀 호출의 반환값을 count에 누적 | 반환값은 정확히 무엇을 세고 있는가? |
| 재귀 호출 이후 자원과 완료 표시를 복원 | 복원하지 않으면 다음 후보의 탐색이 어떻게 달라지는가? |
| can_run에서 자원별로 비교 | 자원의 총합만 비교하면 왜 안 되는가? |

예를 들어 “재귀 호출 후 자원을 감소시킨다”는 동작의 재진술이다. 원리 분석에서는 다음 후보를 같은 출발 상태에서 검사하기 위해 앞선 선택의 영향을 되돌린다는 관계까지 설명해야 한다.

이 질문은 학습·검토용이다. 답안을 암기하거나 이 문서를 제출용 분석으로 그대로 옮기는 대신, 직접 고른 작은 입력으로 상태 변화를 추적하고 자기 말로 설명한다.

## 5. 함수별 작성 절차

1. **역할:** 무엇을 입력받거나 참조하고, 무엇을 반환하거나 변경하는지 적는다.
2. **핵심 원리:** 어떤 조건과 상태 변화로 그 일을 수행하는지 설명한다.
3. **선택 이유:** 핵심 조건이나 연산이 왜 필요한지 설명한다.
4. **확인:** 실제 입력 하나에서 그 설명대로 작동하는지 확인한다.

모든 줄을 같은 길이로 설명할 필요는 없다. 알고리즘의 정확성을 좌우하는 판단·상태 변화·종료 조건에 설명을 집중한다. 제공된 코드와 전역 정의도 공식 요구에 따라 빠짐없이 다룬다.

## 6. 실행결과 분석 절차

1. 실행에 사용한 입력을 기록한다.
2. 실행 전에 예상한 결과와 그 이유를 정리한다.
3. 실제 출력과 예상 결과를 비교한다.
4. 핵심 상태 변화를 추적해 일치하거나 달라진 이유를 설명한다.
5. 실행하지 않은 항목이나 아직 확인하지 못한 조건은 미확인으로 남긴다.

이미 실행한 결과를 분석하는 경우에는 사전 예측을 했다고 꾸미지 않는다. 그 결과가 나오는 이유를 사후에 추적했다는 사실에 맞게 기록한다. 실제로 겪지 않은 오류나 시행착오도 만들지 않는다.

## 7. 판정 방식

각 항목은 점수 대신 다음 세 상태로 표시한다.

- **충족:** 코드·설명·실행 근거가 대응하며 본인이 원리를 설명할 수 있다.
- **보완 필요:** 누락, 불일치 또는 이해가 부족한 부분이 확인되었다.
- **확인 불가:** 작성 과정이나 이해 여부를 확인할 근거가 없다.

기능의 정확성과 본인의 이해는 별도로 평가한다. 설명이 좋아도 코드에 오류가 있을 수 있고, 코드가 맞아도 이해가 부족할 수 있다. 이 기준을 충족했다고 공식 점수나 작성 주체가 자동으로 입증되는 것은 아니다.

### 검토 기록 양식

| 대상 함수·항목 | 점검 기준 | 상태 | 확인 근거 | 보완할 내용 |
|---|---|---|---|---|
| 직접 기입 | 여섯 기준 중 선택 | 충족 / 보완 필요 / 확인 불가 | 코드 위치, 직접 설명, 실행 기록 등 | 직접 기입 |

## 8. 사용하지 않을 방법

- 변수명만 바꾸어 작성 주체가 달라진 것처럼 보이게 하기
- 일부러 어색한 문장이나 오류 넣기
- 겪지 않은 시행착오나 수행하지 않은 테스트 기록하기
- 문체만으로 작성자를 단정하기

이 방법들은 본인 작성과 이해를 입증하지 못한다. 문체는 의미가 정확하고 읽기 쉬운지를 기준으로 다듬는다.
