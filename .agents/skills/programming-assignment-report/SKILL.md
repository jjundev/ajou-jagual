# Programming assignment reports

Help the author produce a report whose requirements, code explanations, and execution analysis agree with the actual assignment and program. Work from the current artifacts rather than replaying a fixed sequence from an earlier assignment.

## Choose the needed work

Identify what the user has requested and which artifacts exist: assignment prompt or rubric, supplied starter code, implemented code, author-written explanation, execution evidence, and final-format file. Do the relevant work below. A request to review a draft does not require recreating it; a Markdown draft does not imply that a required PDF has been checked.

Keep a compact requirement record with `requirement | source and page | evidence | status`. Include scoring weights, hard-fail conditions, submission format, and deadline only when the sources state them. Use statuses that distinguish **confirmed**, **needs author input**, **source conflict**, **not executed**, and **format not verified**. Do not turn an unknown into a pass.

## Use specialist skills when needed

Read and follow a specialist skill only when its task is within the requested scope; these are conditional routes, not a checklist to execute for every report. Keep assignment requirements, code and execution analysis, and final-format verification here. A report request does not by itself authorize external editing or uploads.

- For actual terminal execution screenshots needed as report evidence, use [terminal-evidence-capture](../terminal-evidence-capture/SKILL.md). Capture the current source and cases, with input, observed output, and exit status recorded alongside the images. Do not force screenshots when text logs suffice. If capture is unavailable, report the concrete limitation and distinguish an actual text log from a screenshot; do not fabricate an image or reuse stale evidence as current.
- For user-requested Notion uploads, report formatting, comparisons, targeted edits, image slots, or native HTML downloads and verified PDF printing, use [notion-report-sync](../notion-report-sync/SKILL.md). An upload includes applying and checking the course's default report format. Keep synchronization separate from PDF export and final PDF verification. Capturing a screenshot alone does not authorize uploading it.
- For a cover-only deliverable, use [assignment-cover](../assignment-cover/SKILL.md). For combining a finished report PDF with its cover, use [assignment-report-merge](../assignment-report-merge/SKILL.md); let that skill handle a missing cover rather than creating it twice. Include these tasks only when the requested deliverable calls for them, and follow the specialist's conditions for replacing existing files.
- Use [assignment-report-audit](../assignment-report-audit/SKILL.md) as a separate entry point for a requested comprehensive review, not an automatic step during drafting. When that audit refers here for code and execution analysis, perform that analysis and return to the audit; do not restart the audit or either full workflow recursively.

## Anchor analysis in code and execution

- Compare supplied code with the student's current implementation. Describe a function's inputs, outputs, changed state, and reason for its key conditions or state transitions. Analyze supplied declarations and functions when the rubric requires them. Do not attribute a provided design choice to the student or claim an optimization without measurements or another source.
- Use actual runs for result analysis: record the input, observed output, environment when relevant, and a short trace that explains the result. Choose cases from the assignment examples and material boundaries or errors; never prescribe a fixed test count. Count the cases actually presented separately from internal verification runs; compute any requested totals from the corresponding record.
- If asked to change only comments, preserve executable code and verify that preservation by an appropriate source or token comparison. Re-run focused checks when code changed, evidence became stale, or a required gate needs it. A successful compile, a matching example, and broad correctness are different claims.
- When a current report includes code, compare its code text with the current source after edits. Check every numerical result, return value, and limitation against code or execution evidence. In particular, distinguish a possible future failure from an observed failure.

## Keep the report focused on the assignment

- Build the report body around the required function specifications, code explanations, and actual execution results. For each execution case, connect the required behavior to the input, observed output or screen, and a short causal explanation of the state changes. Additional ordinary execution cases are useful when they demonstrate required behavior that the official examples leave unclear; identify them separately from official examples.
- Write each result analysis as an observed outcome and its code-level cause. Point to the output value, tick, or before-and-after state that supports the explanation. Put expectations in a separate field when the reader needs them for comparison, and keep steps still to be checked in review notes. During handoff review, replace instructions such as “check that the state stays the same” with the observed comparison when evidence exists. Record a missing comparison as unverified.
- Give each part of an execution case a purpose. Output records what the program printed. A state table earns its place by explaining a transition, tracking state the program does not print, or comparing expected and observed results across cases. A caption identifies the case or points out an observed result when the surrounding text does not already do so. Keep the evidence and analysis required by the assignment.
- Use the code in the analysis as the default report source listing. Add a full listing when the assignment or user requests one, or when the report needs source that the analysis does not contain. During review, flag a duplicate listing as an editorial choice and follow the scope of the requested edit.
- Keep internal verification methods and operational records in review material: harnesses, failure injection, randomized or model-based checks, sanitizer diagnostics, aggregate pass counts, source hashes, temporary paths, log wrappers, and screenshot-processing details. Running these checks does not by itself make them report content. If the assignment explicitly requires a testing methodology section or the user specifically requests these details in the report, include only the relevant methods and observed results, with their scope stated.
- Preserve the distinction between code analysis and test methodology. Explain a failure branch and why it preserves state when that explains the actual code or a required behavior; this does not require describing an injected-failure test. Keep actual inputs, outputs, screenshots, and required analyses when removing verification commentary. Avoid repeating generic limits, exit-status summaries, or workflow instructions between cases; state a limitation where it changes the interpretation of a specific result.
- When editing generated manuscripts, update the owning generator and requested editable local variants so regeneration preserves the chosen scope. Determine PDF provenance separately using the workflow below; a request to update local reports does not authorize replacing a Notion-exported PDF with a locally rendered one. Keep verification logs separate and retain existing source and assistance disclosures; simplifying the report is not a reason to invent student intent or conceal authorship.

## Confirm the author's understanding before drafting

- Before writing a new report or substantially rewriting its explanations, inspect the assignment requirements, supplied code, current implementation, and available execution evidence. Then identify the author's understanding needed for the report's core explanations. Code can establish behavior without establishing how the author understands it.
- Ask about key conditions and state changes, a small input trace, or the author's own implementation choices and reasons. Do not present a supplied design as the author's choice. Reuse sufficient explanations already given in conversation or the author's draft; ask only about missing essentials, without a fixed question count or an interview for every function. Routine review, proofreading, and formatting do not require an interview; revisit only understanding affected by substantive changes.
- Use an available question tool to send **one substantive question at a time**, with multiple-choice options, a recommended answer first, and free-text input allowed. In Codex Default mode use `request_user_input_async`; use `request_user_input` only when actually available in Plan mode. Follow the tool's schema, label the recommendation as such, and allow the author to explain in their own words. Ground technical recommendations in the code; recommendations about personal intent are possible suggestions, not established author intent. If no question tool is available, explain that limitation and ask in chat using the same one-question, options-and-recommendation format.
- Wait for the answer before sending the next understanding question or completing the explanation that depends on it. Independent source inspection and execution checks may continue. Elapsed time and a preselected recommendation are not answers.
- Compare the answer with code and execution evidence. If a selection alone leaves a necessary causal explanation unclear, ask for its reason or a small execution example. Follow-up questions also include options and a recommendation while inviting a concrete explanation through free text. Narrow ambiguous answers to one concrete state; explain a misconception briefly, then check another small example. Do not turn this into an endless exam: leave unresolved understanding unconfirmed.
- Reflect the meaning and level of the author's confirmed answers in the relevant report explanation, subject to the assignment's authorship rules. Do not invent intent, understanding, or reflections, copy an incorrect answer into the report, or portray understanding reached after explanation as something the author knew from the start. A suggested option selection alone does not establish independent understanding or authorship.
- If the author skips a question, keep that understanding unconfirmed and defer only the claims that depend on it; verified factual content may proceed. Do not automatically adopt the recommendation, except in the recommended-answer auto mode below. Keep interview working notes separate from the report and do not automatically save verbatim question-and-answer logs to a separate file.

## Recommended-answer auto mode

The author may ask the agent to run unattended to a local manuscript and do only the final edit themselves. This mode is an author-enabled exception to waiting for answers and to not adopting recommendations (above); every other rule in this skill still applies.

- **Activation.** Use this mode only when the current invocation's arguments contain `추천답 모드` or `auto`. Quoted or example text and earlier invocations do not activate it. Without it, use the interview flow above unchanged.
- **Questions.** Still identify the understanding questions the interview flow would ask, but do not send them. Only understanding questions are suppressed: the existing-manuscript and source-conflict questions below are still sent and waited for, using the same tool or chat fallback as the interview flow. A fact the code alone states is written as a fact; only answers to questions the interview flow would actually ask are recorded as adopted. A question is *technical* when the code and runs answer it: what a condition does, which state changes, what a case outputs, why a branch is needed for correct behavior. Adopt the code-grounded recommendation for these. A question is *intent* when it asks why the author chose one design over alternatives, or what they found difficult. Adopt nothing for these: write that cell only from facts the code establishes and leave the intent unstated. A design that came with the supplied code is described as supplied, never as the author's choice, and no optimization is claimed without measurement.
- **Status.** Record every adopted answer as `추천 자동 채택 — 작성자 미확인`, never as confirmed. An adopted recommendation does not establish understanding or authorship.
- **Record.** Keep the usual requirement record in the assignment's `검토자료/요구사항_확인.md`, and add a section listing each adopted answer as `question gist | adopted answer | report location that depends on it`, plus each intent left unstated. Do not save verbatim question-and-answer logs.
- **Sequence.** Requirement record → code and execution analysis → execution screenshots via [terminal-evidence-capture](../terminal-evidence-capture/SKILL.md) for the presented cases → the assignment's manuscript generator → the course prose check in [the course report format](references/data-structures-course-format.md) → the local manuscript (`보고서_노션.md`, or `보고서_노션_자동.md` when an existing file is kept; give the generator its output path). If the assignment has no generator yet, write one in its `검토자료/` that cuts code cells from the current source by line range and inserts actual run output, so regeneration preserves the scope. The generator writes that manuscript directly as Notion-pasteable Markdown; do not create a separate `보고서_초안.md`. Reference screenshots by relative path such as `![](터미널_스크린샷/01-사례.png)`.
- **Existing manuscript.** If `보고서_노션.md` already exists, it may hold the author's own edits. Before generating, ask once with the question tool whether to replace it (backup first; recommended only when the user's request says to regenerate) or keep it and write the new manuscript as `보고서_노션_자동.md`, recommended otherwise. This is a file decision, not an understanding question. On replacement, copy the old file to `검토자료/노션_백업/보고서_노션-backup-<YYYYMMDD-HHMMSS>.md` (create the folder if missing) and list in the handoff the sections where the old and new files differ.
- **Not in this mode.** Do not call Notion APIs, upload, pull, export HTML, print or merge PDFs, create covers, or submit, even when the same request also asks for them. The manuscript still carries unconfirmed adopted answers, so the next stage starts only after the author's final edit: say that a Notion upload is a separate request for [notion-report-sync](../notion-report-sync/SKILL.md). Notion-side formatting (gray TOC, blank-block spacing, page settings, table widths) is `format not verified` until the author pastes and checks it.
- **Source conflict.** When sources conflict in a way that changes implementation, test cases, or grading, record it as `source conflict` with both sources and pages, then ask the author with the question tool (options, recommendation first, free text allowed); a recommendation cannot settle a fact. Independent inspection and runs that do not depend on the value may continue, but do not finish the manuscript on a provisional value.
- **Execution mismatch.** When an execution result differs from the expected output, stop before generating and report the case, the expected and observed output.
- **Capture failure.** When screenshot capture fails or the capture tool is unavailable, continue without that image. Never fabricate one or reuse a stale one. Keep the actual text log labeled as a text log, and name the missing image in the final-edit list.
- **Handoff.** Report the manuscript path actually written, the screenshot files, and a **final-edit list**: `location (section / table row) | adopted answer or unstated intent it relies on | what the author should rewrite in their own words`, including images to insert manually if pasting does not carry them. State the assignment's authorship rule status (for example `작성자 작업 필요` when the prompt requires the student's own writing) and the next steps: author's final edit → paste into Notion → insert images → HTML export → A4 landscape PDF.

## Keep authorship and evidence clear

- Read the assignment's authorship rules. If it requires the student's own writing, use factual notes, focused questions, and feedback on the student's draft; treat assistant-written prose as provisional material, not proof of direct authorship. Do not promise that a style is undetectable or introduce deliberate mistakes to change its appearance.
- Follow the pre-drafting understanding check above for missing author explanations. Selecting a suggested answer or approving a drafted paragraph does not by itself establish independent understanding or authorship.
- Write in a clear, specific level appropriate to the author. Prefer a small state trace and causal explanation over generic praise, line-by-line paraphrase, speculative intent, or polished but unsupported claims.
- Avoid boilerplate prose. Do not open every explanation with the same label line or sentence frame, and do not lean on one connective across cells. Scale depth to importance: the author's implemented functions and central supplied logic get full causal explanation; trivial supplied helpers get one or two sentences. End a result analysis on the behavior the case demonstrates, not on re-adding totals already visible in the output. Course-specific rules, the pre-handoff count, and its threshold live in the course format reference. Varied prose is a readability goal; it is not evidence of authorship, so never present it as making assistant text undetectable, and never invent the author's experiences or confusions to make text sound personal.
- Keep working notes, conflict records, and submission checklists separate from the report body. If an author asks for a review, report concrete issues with locations and repair directions; do not infer the writer from prose style alone.

## Verify the deliverable that actually exists

- For the course above, check the common rubric's mandatory text code and separate report/`.c` submission requirements: code screenshots cannot replace source text in the report (assignment zero), and ZIP submission is treated as non-submission. Run screenshots remain valid execution evidence. Keep the rubric's deferred items out of confirmed checks.
- If the rubric requires a final PDF, verify the exported PDF itself: layout, readable text and execution images, code text selection or extraction, and required sections. Inspect rendered execution pages for the visible command, input, and output when those images support a result claim. A Markdown draft, a Notion page, or a successful export command alone does not prove PDF compliance.
- Use an external editor or Notion only when the user requests it. Treat synchronization and export as separate operations and verify their actual outputs. Never claim submission, upload, or completion based on a local draft.
- Finish with the report's confirmed requirements, unresolved conflicts, missing author work, test scope, and format status. State the exact next step needed for completion. Avoid claiming a grade or that all possible inputs were validated.

## Skill check before reuse

When revising this skill, test it against at least these distinct situations: conflicting PDF render/extraction; a report that invents a performance rationale for supplied code or miscounts recorded tests; and a sound Markdown draft whose required PDF has not been rendered or checked. Keep assignment-specific fixtures and service adapters outside this skill unless repetition demonstrates a need for a reusable resource.

Also check the interview flow: a new report with missing core understanding prompts one tool question with options and a recommendation before the dependent explanation; a selection without sufficient reasoning receives a focused follow-up; incorrect or ambiguous answers receive explanation and rechecking; no response stays pending and a skipped question stays unconfirmed without automatic recommendation adoption; sufficient prior answers and formatting-only requests do not trigger repeated interviews; and a missing question tool produces an explicit chat fallback with the same question format. Distinguish simulated behavior checks from live question-tool UI verification.

Also check the recommended-answer auto mode: with `추천답 모드` in the arguments, no understanding question is sent, adopted answers are recorded as unconfirmed with their report locations, and the final-edit list matches that record; personal-intent questions are not adopted and their cells stay factual; a source conflict that changes implementation or grading still asks the author and is not finished on a provisional value; a capture failure continues without the image and lists the gap; no Notion call is made even when the request also asks for an upload; an existing `보고서_노션.md` prompts one replace-or-keep question and is backed up before any replacement. Without the keyword, or with it only in quoted text, the first understanding question is sent as usual.

Also check specialist routing: text-log-only and local-draft requests do not trigger screenshots or unrelated Notion, upload, cover, or merge work; needed terminal screenshots use the capture skill with current evidence and an honest unavailable-capture fallback; requested Notion work uses its specialist without claiming PDF export; cover-only work and a finished-PDF merge with a missing cover take their respective routes without duplicate cover creation; and an audit-originated analysis returns without recursive workflow invocation. Distinguish simulated routing checks from actual terminal, Notion, and PDF operations.

Also check report scope: with official examples, additional ordinary cases demonstrating required behavior, and extensive internal verification available, the default report presents the relevant actual cases without importing internal pass totals or tool details. A request to remove extra verification preserves these cases and code-level failure explanations. An explicit requirement or user request for testing methodology includes the relevant checks without presenting them as mandatory assignment work. Regenerating edited local reports must retain that separation.

Also check prose style: given a generated draft whose explanation cells all start with the same parameter/return label and whose most frequent connective appears in most cells, the skill rewrites before handoff, keeps the spec sentence only for implemented functions, shortens trivial supplied helpers, records the counts in review notes, and adds no invented author experiences. A draft already below the course threshold needs no variety-only rewrite. During this prose pass, preserve code cells, outputs, and state tables.

Also check execution presentation separately from the prose counts: a failed command with unchanged state is reported from the actual before-and-after evidence. A pending check stays unverified. Preserve distinct state transitions when condensing a repeated output table, omit a redundant caption when the case is already identified, and keep a required full listing. A tiny capture in a final PDF needs a legibility check on the rendered page and a fix within the requested export scope. A real wrapper-based run retains its provenance when relevant.

Also check PDF provenance: local-only edits preserve the previous PDF and leave Notion reflection/export pending; authorized Notion edits alone do not silently generate a PDF; a complete course-report export uses the genuine Notion HTML ZIP and bundled assets followed by A4 landscape printing. An unavailable native PDF orientation selector does not block this HTML route. A locally authored HTML draft is not a substitute for a Notion export. Preserve default font/appearance, original export bytes and content, and record each stage accurately; review records must match their PDF.
