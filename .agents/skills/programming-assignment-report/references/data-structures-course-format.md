# 자료구조 및 알고리즘 이해: 반복 보고서 양식

이 문서는 [2026-2] 자료구조 및 알고리즘 이해의 프로그래밍 과제 보고서에만 적용한다. 먼저 [공통 채점기준](course-rubric.md)과 현재 과제의 공식 지시를 확인한다. 아래의 작성자 선호는 필수 조건 안에서 조정할 수 있으며 공식 요구를 면제하지 않는다. 과제1의 함수명, 사례 수, 날짜, 획득 점수는 재사용하지 않는다. 공통 채점기준의 배점은 같은 학기·과목 범위에서 재사용한다.

공식 조건은 함수별 왼쪽 코드·오른쪽 분석, 기능·동작 원리 분석, 전역변수·매크로·구조체 등 앞단 선언 분석, 보고서 코드의 텍스트 작성이다. 선언부 분석은 주석으로 대체할 수 있으나 함수 분석에는 이 예외를 적용하지 않는다. A4 가로, 별도 표지, 목차·제목·간격, 페이지 번호 생략, 실행 화면 배치는 이 문서의 작성자 선호이며 공통 채점표의 명시 조건으로 표시하지 않는다.

## 작성 사례

[과제1 Notion 보고서 Markdown](../../../../과제/과제1/보고서_노션.md)은 제목 계층, 코드 분석 표, 실행 증빙 배치를 확인하는 실제 작성 사례다. 후속 과제의 본문 템플릿이나 PDF 검증 결과로 취급하지 않는다. 이 파일의 Notion 이미지 링크는 만료될 수 있으므로 이미지의 장기 보존 근거로 삼지 않는다.

[과제1 최종 제출 사례](hw1-case-study.md)에는 사용자가 실제 제출본으로 확인한 PDF·C 보존 사본, 만점 결과의 출처, PDF 페이지 안내, 구체적인 분석 예시와 실행 근거가 있다. 최종 배치는 보존 PDF에서, 편집 구조는 위 Markdown에서 확인한다. 재사용할 설명 방식과 과제1에만 해당하는 조건은 사례 문서에서 구분한다.

[과제3 제출 PDF](../../../../과제/과제3/제출용/HW3_202220953_신현준.pdf)는 함수의 중요도에 따른 설명 분량(6, 10–11쪽)과 실행값에서 원인을 설명하는 방식(16, 19–21쪽)의 참고 사례다. 예를 들어 19쪽은 T2의 `R0 Q0`에서 완료를 먼저 처리해 다음 tick에 P2가 실행됐음을 설명한다. 제출본의 부록·캡처 크기·사례 수는 현재 과제의 기준으로 삼지 않는다.

## Notion 본문

- 과제1에서 확인한 기본 페이지 설정을 적용한다: **기본 글꼴, 작은 텍스트 끔, 전체 너비 켬**. 실제 노션 화면에서 선택 상태를 확인하고 새로고침 후 유지되는지 검사한다. Markdown이나 블록 API 응답만으로 이 설정을 확인했다고 기록하지 않는다. 사용자가 다른 설정을 지정하면 해당 설정을 우선한다.
- 본문은 **회색 자동 목차 1개**로 시작한다. 기존 목차가 있으면 재사용하거나 지정한 목차만 남기고, 새 목차를 중복 생성하지 않는다. 대단원은 번호 없는 제목 1, 소단원은 번호 없는 제목 2로 두고 목차에 둘 다 표시한다. 한 소단원 아래 여러 실행 화면을 묶을 때는 제목 3을 사용할 수 있다. 제목 이름과 개수는 과제 요구에 맞춘다.
- 각 실행 사례에서 반복되는 ‘입력’, ‘실제 출력’, ‘실제 터미널 실행 화면’ 표시는 굵은 일반 문단으로 둔다. 반복 표시만을 제목 3으로 만들어 목차에 쌓지 않는다. 의미 있는 하위 사례 구분에는 위 제목 3 규칙을 적용할 수 있다.
- 목차와 첫 대단원 사이 빈 블록은 한 칸, 대단원 사이는 두 칸, 같은 대단원의 소단원 사이는 한 칸이다. 대단원 바로 뒤 첫 소단원에는 빈 블록을 더하지 않는다. 실행 단원의 도입·검증 범위 설명 문단 뒤에 첫 사례가 나오면 그 사이에는 한 칸을 둔다. 실행 사례 내부 간격은 아래 규칙을 적용하고, 나머지 출력·이미지·표·분석 사이에는 빈 블록을 기계적으로 삽입하지 않는다. 작성자가 정한 수동 줄바꿈과 표 셀 안 항목 순서를 임의로 정리하지 않는다.
- 학번·이름·보고서 제목은 별도 표지에 둔다. 상세 실행 환경은 실제 빌드 근거와 확인 범위에 맞춰 기록한다. 본문 첫머리에 학생 정보나 기계적인 실행 방식 안내를 자동 복원하지 않는다.
- 노션 업로드 요청 시 이 서식을 최초 업로드 과정에 함께 적용하고, 제목·간격은 실제 블록으로, 페이지 설정은 실제 화면으로 검증한다. 과제1·2의 페이지 ID, 제목 수, 표·이미지 수나 빈 블록 총개수를 후속 과제에 고정하지 않는다.

## 코드와 실행 근거

- 소스 분석은 함수별 편집 가능한 2열 표를 기본으로 한다. 왼쪽에 실제 소스와 일치하는 텍스트 코드, 오른쪽에 같은 행 코드의 기능 명세와 동작 원리 분석을 둔다. 긴 함수는 코드와 설명의 대응을 유지하면서 여러 행으로 나눌 수 있다. 전역변수·매크로·구조체 등 앞단 선언도 공통 기준에 따라 분석한다. 함수 원형 등 추가 범위는 현재 과제에 맞춰 정한다.
- 표 머리행에는 ‘소스코드’와 ‘기능 명세와 분석’을 두고, 설명 셀 안에는 ‘기능 명세와 분석’, ‘기능 명세’, ‘분석 (계속)’ 같은 반복 표제를 붙이지 않는다. 설명은 해당 코드의 내용으로 바로 시작한다. 구현 함수는 첫 문장에서 인자·반환값·바뀌는 상태 등 기능 명세를 밝히며, 짧은 ‘인자: … 반환값: …’ 한 줄로 써도 된다. 제공 함수에는 이런 머리말 줄을 붙이지 않고 동작과 이유부터 쓰며, 반환값처럼 필요한 명세는 문장 안에 넣는다. 모든 설명 칸을 같은 문장 틀로 시작하지 않는다. 표제 생략이 명세·원리 분석 생략을 뜻하지 않는다.
- 설명 분량은 코드의 중요도에 맞춘다. 구현 함수와 동작의 중심이 되는 제공 함수(main, 실행·상태 전이 함수, 자료구조 조작 함수)는 조건과 상태 변화의 이유까지 쓰고, 한두 줄짜리 초기화·검사 함수는 1~2문장으로 끝낸다. 구현 목적은 1~2문장으로 쓰고 세부는 본문에 맡긴다.
- 연결어 하나에 기대지 않는다. ‘~므로’, ‘~때문에’ 같은 인과 연결어나 같은 문장 끝맺음이 설명 칸마다 되풀이되면 이음말·어미·문장 순서를 바꿔 쓴다. 원고를 넘기기 전에 함수·선언 설명 칸과 결과 분석(코드 칸·부록 소스·사례 상태 표 제외)에서 가장 많이 쓴 인과·전환 연결어(‘~므로’, ‘~때문에’, ‘따라서’, ‘즉’, ‘이어서’ 등. 나열 어미 ‘-고’·‘-며’는 세지 않는다) 3개의 횟수와 설명 칸 수, 구현 함수 밖의 ‘인자:’ 머리말 수를 세어 검토 기록에 남긴다. 가장 많이 쓴 연결어가 설명 칸 수의 1/3을 넘거나 제공 함수에 머리말 줄이 있으면 넘기기 전에 다시 쓴다. 참고값으로 과제1 최종본은 ‘므로’가 3.6만 자에 14회(1000자당 약 0.4회)였다. 이 점검은 읽기 좋은 글을 위한 것이며 작성자가 직접 썼다는 근거나 판정 회피의 보장이 아니다.
- Notion 코드 셀의 서식과 들여쓰기는 [notion-report-sync의 Code in table cells](../../notion-report-sync/SKILL.md#code-in-table-cells) 규칙을 따른다.
- 코드의 원래 줄바꿈을 보존한다. PDF에서 폭 때문에 생기는 추가 자동 줄바꿈은 줄이되 코드 내용을 바꾸지 않는다. 여러 페이지에 걸친 표는 행 사이에서 넘길 수 있으나 같은 행의 코드와 분석을 서로 다른 페이지에 두지 않는다.
- 코드·설명 열 너비는 표마다 실제 내용에 맞춰 조정한다. 긴 코드의 불필요한 자동 줄바꿈을 줄이면서 설명도 읽을 수 있게 배분하고, 노션 화면에서 확인한다. 모든 표에 같은 비율을 강제하거나 이전 과제의 너비 숫자를 고정값으로 재사용하지 않는다. Markdown에 `<colgroup>`·`<col width>`가 있으면 비교 근거로 기록하되, 지정값이 없는 열을 너비 0으로 해석하지 않는다. PDF 배치는 내보낸 PDF에서 별도로 확인한다.
- 함수 분석표의 텍스트 코드로 보고서에 필요한 소스가 충족되는지 먼저 확인한다. 현재 과제에서 전체 소스 수록을 요구하거나 작성자가 원할 때, 또는 분석표에 없는 소스를 보고서에 함께 제시해야 할 때 전체 코드 부록을 둔다. 별도 `.c` 제출 요건은 공통 채점기준을 적용한다.
- 개별 실행 사례에는 입력, 실제 출력 텍스트, 실제 터미널 실행 화면, 결과 분석을 가까이 둔다. 상태·계산 표는 실행 순서, 큐·스택 변화, 판단에 필요한 계산처럼 출력만으로 읽기 어려운 정보를 더할 때 쓴다. 여러 경계값·예외 사례는 과제1의 14쪽처럼 기대 동작과 실제 결과를 나란히 놓은 표로 묶을 수 있다. 사례 수와 이미지 수는 실제 과제와 검증 범위에서 정한다.
- 결과 분석은 관찰값을 짚고, 해당 조건과 상태 변화로 이유를 설명한다. 실패 전후의 상태가 같다면 두 상태를 대조한 결과와 상태 변경 전에 반환하는 분기 등 코드에서 확인한 이유를 쓴다. ‘같아야 한다’, ‘유지되는지 확인한다’ 같은 검증 문장이 결과에 섞였는지 원고를 넘기기 전에 확인한다. 기대 동작은 비교 표에, 미실행 검증은 검토 기록에 둔다. 출력의 합계나 tick 수는 그 값이 사례의 원인을 설명하는 데 필요할 때 인용한다.
- 각 사례에서 입력 코드 블록과 ‘실제 출력’ 표제 사이, 출력·종료 상태 기록과 ‘실제 터미널 실행 화면’ 표제 사이에 **실제 빈 문단 블록을 각각 1개** 둔다. 마지막 사례에도 같은 규칙을 적용한다. 표제와 그 내용 사이에는 추가 빈 블록을 넣지 않는다. 인접한 소단원 제목이나 필요한 캡션으로 사례를 식별한다.
- 화면은 한 줄에 한 장씩 읽을 수 있는 크기로 배치한다. 인접한 제목으로 사례가 식별되고 캡션이 정보를 더하지 않으면 생략한다. 캡션이 필요하면 사례 이름이나 실제로 확인한 핵심 결과를 적는다. 새로 캡처할 때 제출용 빌드를 직접 실행해 같은 사례를 재현할 수 있으면 그 실제 실행 화면을 사용한다. 실행 래퍼가 필요한 사례는 실제 실행 맥락을 유지한다. 원본 캡처, 실제 명령, 작업 경로와 종료 상태 등 자세한 근거는 검토 기록에 보존한다.
- 스크린샷은 실행 근거다. 제출 보고서의 소스코드는 이미지로 대체하지 않는다.

## PDF 확인

- Notion의 기본 글꼴·기본 모드 HTML을 이미지와 함께 내보내고, 다운로드한 실제 HTML을 A4 가로 PDF로 인쇄한다. Notion 자체 PDF 내보내기에 가로 방향 옵션이 있다고 가정하지 않는다. 원본 ZIP·HTML·이미지는 보존하고, 인쇄용 사본의 여백·페이지 나눔·표 폭만 조정한다. 로컬에서 별도로 작성한 HTML을 Notion 내보내기 원본으로 대체하지 않는다. 별도의 A4 가로 표지 제작·병합은 요청된 범위에서 진행한다. 페이지 번호와 브라우저 머리말·꼬리말은 넣지 않는다.
- 내보낸 PDF에서 코드와 분석의 좌우 대응, 텍스트 코드의 선택·추출, 코드 들여쓰기 유지, 코드 글자색, 코드 자동 줄바꿈, 행 분리, 머리행 반복 여부, 제목만 남는 페이지, 넓은 표와 스크린샷의 가독성을 확인한다. 필요하면 정한 간격을 유지하면서 페이지 나누기·열 너비·행 높이를 조정한다.
- Notion 화면, Markdown, 본문 PDF, 병합 PDF, 실제 제출을 서로 다른 상태로 기록한다. 파일을 직접 확인하기 전에는 PDF 양식이나 제출을 통과로 표시하지 않는다.
