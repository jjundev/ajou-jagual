# 자료구조 및 알고리즘 이해: 반복 보고서 양식

이 문서는 [2026-2] 자료구조 및 알고리즘 이해의 프로그래밍 과제 보고서에만 적용한다. 먼저 [공통 채점기준](course-rubric.md)과 현재 과제의 공식 지시를 확인한다. 아래의 작성자 선호는 필수 조건 안에서 조정할 수 있으며 공식 요구를 면제하지 않는다. 과제1의 함수명, 사례 수, 날짜, 획득 점수는 재사용하지 않는다. 공통 채점기준의 배점은 같은 학기·과목 범위에서 재사용한다.

공식 조건은 함수별 왼쪽 코드·오른쪽 분석, 기능·동작 원리 분석, 전역변수·매크로·구조체 등 앞단 선언 분석, 보고서 코드의 텍스트 작성이다. 선언부 분석은 주석으로 대체할 수 있으나 함수 분석에는 이 예외를 적용하지 않는다. A4 가로, 별도 표지, 목차·제목·간격, 페이지 번호 생략, 실행 화면 배치는 이 문서의 작성자 선호이며 공통 채점표의 명시 조건으로 표시하지 않는다.

## 작성 사례

[과제1 Notion 보고서 Markdown](../../../../과제/과제1/보고서_노션.md)은 제목 계층, 코드 분석 표, 실행 증빙 배치를 확인하는 실제 작성 사례다. 후속 과제의 본문 템플릿이나 PDF 검증 결과로 취급하지 않는다. 이 파일의 Notion 이미지 링크는 만료될 수 있으므로 이미지의 장기 보존 근거로 삼지 않는다.

[과제1 최종 제출 사례](hw1-case-study.md)에는 사용자가 실제 제출본으로 확인한 PDF·C 보존 사본, 만점 결과의 출처, PDF 페이지 안내, 구체적인 분석 예시와 실행 근거가 있다. 최종 배치는 보존 PDF에서, 편집 구조는 위 Markdown에서 확인한다. 재사용할 설명 방식과 과제1에만 해당하는 조건은 사례 문서에서 구분한다.

[과제3 제출 PDF](../../../../과제/과제3/제출용/HW3_202220953_신현준.pdf)는 함수의 중요도에 따른 설명 분량(6, 10–11쪽)과 실행값에서 원인을 설명하는 방식(16, 19–21쪽)의 참고 사례다. 예를 들어 19쪽은 T2의 `R0 Q0`에서 완료를 먼저 처리해 다음 tick에 P2가 실행됐음을 설명한다. 제출본의 부록·캡처 크기·사례 수는 현재 과제의 기준으로 삼지 않는다.

서술 형식의 기준 사례는 [과제3 보고서 Markdown](../../../../과제/과제3/보고서_노션.md)과 [과제4 보고서 Markdown](../../../../과제/과제4/보고서_노션.md)(2026-11-16 재작성본)이다. 설명 칸의 `#기능 명세`/`#분석` 표시와 `•` 항목, 짧은 함수의 한 줄 칸, `**결과 분석:**` 문단을 여기서 확인한다. 과제4 첫 초안은 칸 안 표제를 빼고 문단으로 쓰다가 칸당 문장이 과제3의 약 2배(4.9 대 2.7)가 되어 작성자가 이 형식으로 다시 쓰게 했다. 이후 과제4 노션 수정에서는 검산용 쪽수·예시 일치 문구(`N쪽 조건대로`, `N쪽 화면과 같다`), 출제 의도 추측, 미발생 예외 경고, 과도한 압축 종결어미를 덜어 내고 풀어진 평서문과 제공/구현 시점 분리를 적용했다.

## Notion 본문

- 과제1에서 확인한 기본 페이지 설정을 적용한다: **기본 글꼴, 작은 텍스트 끔, 전체 너비 켬**. 실제 노션 화면에서 선택 상태를 확인하고 새로고침 후 유지되는지 검사한다. Markdown이나 블록 API 응답만으로 이 설정을 확인했다고 기록하지 않는다. 사용자가 다른 설정을 지정하면 해당 설정을 우선한다.
- 본문은 **회색 자동 목차 1개**로 시작한다. 기존 목차가 있으면 재사용하거나 지정한 목차만 남기고, 새 목차를 중복 생성하지 않는다. 대단원은 번호 없는 제목 1, 소단원은 번호 없는 제목 2로 두고 목차에 둘 다 표시한다. 한 소단원 아래 여러 실행 화면을 묶을 때는 제목 3을 사용할 수 있다. 제목 이름과 개수는 과제 요구에 맞춘다.
- 각 실행 사례에서 반복되는 ‘입력’, ‘실제 출력’, ‘실제 터미널 실행 화면’ 표시는 굵은 일반 문단으로 둔다. 반복 표시만을 제목 3으로 만들어 목차에 쌓지 않는다. 의미 있는 하위 사례 구분에는 위 제목 3 규칙을 적용할 수 있다.
- 목차와 첫 대단원 사이 빈 블록은 한 칸, 대단원 사이는 두 칸, 같은 대단원의 소단원 사이는 한 칸이다. 대단원 바로 뒤 첫 소단원에는 빈 블록을 더하지 않는다. 실행 단원은 기본으로 도입 문단(`과제 N·M쪽의 공식 예시 K건을 실행했다.` 등)을 두지 않고 대단원 제목 바로 아래 첫 사례 소단원으로 시작하며, 여러 사례 범주를 묶어 안내해야 할 때만 1문장 도입 문단을 두고 그 아래에 빈 블록 한 칸을 둔다. 실행 사례 내부 간격은 아래 규칙을 적용하고, 나머지 출력·이미지·표·분석 사이에는 빈 블록을 기계적으로 삽입하지 않는다. 작성자가 정한 수동 줄바꿈과 표 셀 안 항목 순서를 임의로 정리하지 않는다.
- 학번·이름·보고서 제목은 별도 표지에 둔다. 상세 실행 환경은 실제 빌드 근거와 확인 범위에 맞춰 기록한다. 본문 첫머리에 학생 정보나 기계적인 실행 방식 안내를 자동 복원하지 않는다.
- 노션 업로드 요청 시 이 서식을 최초 업로드 과정에 함께 적용하고, 제목·간격은 실제 블록으로, 페이지 설정은 실제 화면으로 검증한다. 과제1·2의 페이지 ID, 제목 수, 표·이미지 수나 빈 블록 총개수를 후속 과제에 고정하지 않는다.

## 코드와 실행 근거

- 소스 분석은 함수별 편집 가능한 2열 표를 기본으로 한다. 왼쪽에 실제 소스와 일치하는 텍스트 코드, 오른쪽에 같은 행 코드의 기능 명세와 동작 원리 분석을 둔다. 표 소스 칸에서는 주석(`/* */`·`//`, 제공 코드의 주석 포함)을 빼고, 주석 때문에 빈 줄이 된 줄도 뺀다. 주석만 지우고 줄바꿈은 소스대로 두므로, 남은 줄은 제출 `.c`와 글자가 같아야 한다. 참고 구현은 [과제4 생성기](../../../../과제/과제4/검토자료/build_report.py)의 `strip_comments`다. 긴 함수는 코드와 설명의 대응을 유지하면서 여러 행으로 나눌 수 있다. 전역변수·매크로·구조체 등 앞단 선언도 공통 기준에 따라 분석한다. 함수 원형 등 추가 범위는 현재 과제에 맞춰 정한다.
- 함수 소단원 제목은 함수 이름으로 하고, 직접 작성한 함수만 `insert_timer (구현)`처럼 `(구현)`을 붙인다. 제목 아래에 ‘제공 함수’·‘직접 작성한 함수’ 같은 구분 문단은 두지 않는다.
- 표 머리행에는 ‘소스코드’와 ‘기능 명세와 분석’을 둔다. 설명 칸은 `#기능 명세` 줄 아래 `•` 항목, 빈 줄, `#분석` 줄 아래 `•` 항목 순서로 쓴다(Markdown에서는 `<br>`로 줄을 나눈다). `#기능 명세`에는 무엇을 하고 무엇을 돌려주는지를, `#분석`에는 핵심 조건과 그 이유를 쓴다. 항목 하나는 한두 문장이고, 조건과 이유를 한 항목에 묶는다. 한 함수를 여러 행으로 나눴다면 둘째 행부터는 `#분석`만 써도 된다. 한두 줄짜리 함수는 `#기능 명세` 한 항목으로 끝내고 `#분석`을 두지 않는다. 예: 과제3 `init_stack` 칸은 ‘• top = -1로 빈 스택을 만든다.’ 한 줄, 과제3 `select_process`·과제4 `insert_timer` 칸은 기능 명세 2항목과 분석 3~4항목이다.
- 설명 분량은 코드의 중요도에 맞춘다. 구현 함수와 동작의 중심이 되는 제공 함수(main, 실행·상태 전이 함수, 자료구조 조작 함수)는 조건과 상태 변화의 이유까지 쓰고, 한두 줄짜리 초기화·검사 함수는 1~2문장으로 끝낸다. 함수 설명 칸 평균은 약 220자 안팎이 기준이고(과제3 220자, 과제4 213자), 비중이 큰 함수라도 `#분석` 항목은 4개 안팎으로 둔다. 작성자의 구현 과정·이해를 반영할 때도 문단을 늘리지 않고 핵심 ‘왜’를 한 항목 한 문장으로 넣는다. 구현 목적은 1~2문장으로 쓰고 세부는 본문에 맡긴다.
- 작성자가 소스에 쓴 주석은 그 함수 설명 칸의 근거로 쓴다. 주석 내용을 `#기능 명세`/`#분석` 항목에 평서문으로 옮기고, 질문형 주석('…인가?')은 코드로 확인한 답으로 적되 제공 함수에 대한 작성자의 이해·해석 관점이 주석이나 답변에 실제로 드러난 경우(`~라는 의도로 이해했다` 등)에는 그 시점을 살릴 수 있다. 미확인 제공 함수는 추측이나 설계자 어조 없이 관찰된 동작만 담백하게 쓰고, 표에는 주석이 없어 가리킬 곳이 없으므로 칸에 '주석'이라는 말이나 '(코드 위 주석)' 같은 참조는 쓰지 않는다. 주석의 내용이 코드와 다르면 옮기지 않고 검토 기록에 사유를 남긴다. 예: 과제4 read_timers의 ‘최초 1회만 바꾸는건가?’ → ‘값이 실제로 바뀌는 건 첫 삽입(NULL → 첫 노드) 한 번뿐이다.’, print_timers의 가지치기 메모 → ‘from보다 작으면 왼쪽, to보다 크면 오른쪽 서브트리를 볼 필요가 없지만 요구사항에 없어 넣지 않았다.’
- 문체는 압축 요약 종결어미(`~서다`, `~잡는다`, `~부른다`) 대신 이유절과 서술어를 풀어 쓴 자연스러운 평서문(`~했기 때문이다`, `~할 수 있다`, `~호출한다`, `~간주한다`)을 기본으로 삼는다. 출력 형식 경계가 필요하면 `[TIMER 만료시각 id]`처럼 대괄호로 구분할 수 있고, 가짜 수업 경험·과장된 감탄(`센스있게`)·고의 오탈자(`어짜피`)는 넣지 않는다.
- 검산·대조·출제 의도 추측·미발생 예외 경고 문장은 생성 단계에서 쓰지 않는다. ‘12쪽 조건대로 함수를 새로 만들지 않았다’, ‘(공식 예시 1의 25(02))’, ‘출력 형식을 고정하려고 제공된 함수다’, ‘정상 동작에서는 가지 않는 분기다’, ‘검사가 없으면 NULL을 역참조한다’ 같은 문장은 보고서 본문에서 빼고, 특정 함수 제외 근거처럼 범위를 밝혀야 하는 경우에만 최소한의 쪽수를 둔다. 본문 셀 안에는 `[개인 의도 추가]` 같은 미완성 빈칸을 남기지 않고 사실 문장으로 완결한 뒤, 개인 동기나 수업 맥락을 보탤 만한 자리만 `final-edit list`에 안내한다.
- 연결어 하나에 기대지 않는다. ‘~므로’, ‘~때문에’ 같은 인과 연결어나 같은 문장 끝맺음이 설명 칸마다 되풀이되면 이음말·어미·문장 순서를 바꿔 쓴다. 원고를 넘기기 전에 함수·선언 설명 칸과 결과 분석(코드 칸·부록 소스·사례 상태 표 제외)에서 가장 많이 쓴 인과·전환 연결어(‘~므로’, ‘~때문에’, ‘따라서’, ‘즉’, ‘이어서’ 등. 나열 어미 ‘-고’·‘-며’는 세지 않는다) 3개의 횟수와 설명 칸 수를 세어 검토 기록에 남긴다. 가장 많이 쓴 연결어가 설명 칸 수의 1/3을 넘으면 넘기기 전에 다시 쓴다. 참고값으로 과제1 최종본은 ‘므로’가 3.6만 자에 14회(1000자당 약 0.4회)였다. 이 점검은 읽기 좋은 글을 위한 것이며 작성자가 직접 썼다는 근거나 판정 회피의 보장이 아니다.
- 구현 함수의 `#기능 명세`는 `• 인자: … / 반환값: …`과 `• 상태 변경: …` 두 항목으로 시작한다(트리를 바꾸지 않으면 ‘상태 변경: 없음’). 제공 함수는 동작부터 쓰고 반환값처럼 필요한 명세는 항목 문장 안에 넣는다. 반환값·상태 변경이 흐름을 바꾸는 제공 함수(과제3의 `enqueue`·`execute_tick`처럼)만 `인자:`·`반환값:` 항목을 쓸 수 있고, 그런 칸은 제공 함수 수의 1/3 이하로 둔다. 참고 실패 사례: 과제2 초안은 구현 함수와 제공 함수를 합한 12개 설명 칸 전부가 표시 없이 "인자: … 반환값: … 변경 상태: …" 문장으로 시작해 틀 반복으로 지적됐다.
- 실행 화면 캡션이 두 장 이상에서 글자 그대로 같으면 캡션을 모두 삭제하고 인접한 소단원 제목으로 사례를 식별한다. 캡션을 남길 사례는 그 사례에서 실제로 관찰한 결과를 서로 다른 문장으로 쓴다. 참고 실패 사례: 과제2 초안은 캡션 6장이 "터미널의 실제 실행 화면. 명령별 처리 결과와 메모리 지도를 보여 준다."로 완전히 같아 지적됐다.
- Notion 코드 셀의 서식과 들여쓰기는 [notion-report-sync의 Code in table cells](../../notion-report-sync/SKILL.md#code-in-table-cells) 규칙을 따른다.
- 코드의 원래 줄바꿈을 보존한다. PDF에서 폭 때문에 생기는 추가 자동 줄바꿈은 줄이되 코드 내용을 바꾸지 않는다. 여러 페이지에 걸친 표는 행 사이에서 넘길 수 있으나 같은 행의 코드와 분석을 서로 다른 페이지에 두지 않는다.
- 코드·설명 열 너비는 표마다 실제 내용에 맞춰 조정한다. 긴 코드의 불필요한 자동 줄바꿈을 줄이면서 설명도 읽을 수 있게 배분하고, 노션 화면에서 확인한다. 모든 표에 같은 비율을 강제하거나 이전 과제의 너비 숫자를 고정값으로 재사용하지 않는다. Markdown에 `<colgroup>`·`<col width>`가 있으면 비교 근거로 기록하되, 지정값이 없는 열을 너비 0으로 해석하지 않는다. PDF 배치는 내보낸 PDF에서 별도로 확인한다.
- 함수 분석표의 텍스트 코드로 보고서에 필요한 소스가 충족되는지 먼저 확인한다. 현재 과제에서 전체 소스 수록을 요구하거나 작성자가 원할 때, 또는 분석표에 없는 소스를 보고서에 함께 제시해야 할 때 전체 코드 부록을 둔다. 부록은 제출 `.c` 원문을 주석까지 그대로 싣는다(작성자 결정, 2026-11-16). 별도 `.c` 제출 요건은 공통 채점기준을 적용한다.
- 개별 실행 사례에는 입력, 실제 출력 텍스트, 실제 터미널 실행 화면, 결과 분석을 가까이 둔다. 상태·계산 표는 실행 순서, 큐·스택 변화, 판단에 필요한 계산처럼 출력만으로 읽기 어려운 정보를 더할 때 쓴다. 여러 경계값·예외 사례는 과제1의 14쪽처럼 기대 동작과 실제 결과를 나란히 놓은 표로 묶을 수 있다. 실행 사례는 과제가 준 실행 예시만 싣는다. 예시가 없는 과제는 요구된 기능마다 정상 동작 하나를 싣는다. 경계값·오류 확인 실행은 검토 기록에 두고, 공식 예시가 보여 주지 않는 동작은 함수 설명 칸 분석에서 다룬다. 추가 사례는 과제가 요구하거나 작성자가 요청할 때만 넣고, 소단원 제목으로 무엇을 보이는 사례인지 드러내며 제목 아래에 따로 목적 문단을 두지 않는다. 과제4에서 작성자가 추가 사례 3건을 '굳이 없어도 된다'며 뺐다(2026-11-16). 상태 표의 칸도 ‘10(04) ≤ 25 → 잎이라 free’처럼 짧게 쓴다.
- 결과 분석은 `**결과 분석:**` 굵은 표시로 시작하는 1~3문장 문단이다. 관찰값을 짚고, 해당 조건과 상태 변화로 이유를 설명한 뒤 끝낸다(‘출력과 트리 모양이 10쪽 화면과 같다’ 같은 과제 PDF 대조 문장으로 닫지 않는다). 실패 전후의 상태가 같다면 두 상태를 대조한 결과와 상태 변경 전에 반환하는 분기 등 코드에서 확인한 이유를 쓴다. ‘같아야 한다’, ‘유지되는지 확인한다’ 같은 검증 문장이 결과에 섞였는지 원고를 넘기기 전에 확인한다. 기대 동작은 비교 표에, 미실행 검증은 검토 기록에 둔다. 출력의 합계나 tick 수는 그 값이 사례의 원인을 설명하는 데 필요할 때 인용한다.
- 각 사례에서 입력 코드 블록과 ‘실제 출력’ 표제 사이, 출력·종료 상태 기록과 ‘실제 터미널 실행 화면’ 표제 사이에 **실제 빈 문단 블록을 각각 1개** 둔다. 마지막 사례에도 같은 규칙을 적용한다. 표제와 그 내용 사이에는 추가 빈 블록을 넣지 않는다. 인접한 소단원 제목이나 필요한 캡션으로 사례를 식별한다.
- 화면은 한 줄에 한 장씩 읽을 수 있는 크기로 배치한다. 인접한 제목으로 사례가 식별되고 캡션이 정보를 더하지 않으면 생략한다. 캡션이 필요하면 사례 이름이나 실제로 확인한 핵심 결과를 적는다. 새로 캡처할 때 제출용 빌드를 직접 실행해 같은 사례를 재현할 수 있으면 그 실제 실행 화면을 사용한다. 실행 래퍼가 필요한 사례는 실제 실행 맥락을 유지한다. 원본 캡처, 실제 명령, 작업 경로와 종료 상태 등 자세한 근거는 검토 기록에 보존한다.
- 스크린샷은 실행 근거다. 제출 보고서의 소스코드는 이미지로 대체하지 않는다.

## 넘기기 전 저자성 흔적 점검

원고를 Notion에 올리거나 PDF로 내보내기 전에, 아래 여섯 가지를 세어 검토 기록에 남긴다. 각 수치가 임계값을 넘으면 그 자리에서 고치거나 작성자 수정 항목으로 **final-edit list**에 올린다. 이 점검은 작성자가 직접 썼다는 근거가 아니라, "같은 틀로 찍어낸 것처럼 읽히는 자리"를 사전에 드러내기 위한 것이다. 통과한 과제1 패턴을 모방한다고 저자성이나 AI 판정 회피가 보장되지 않는다.

1. **칸 형식·분량** — `인자:` 항목을 쓴 제공 함수 수(제공 함수 수의 1/3 이하), 함수 설명 칸 평균 글자 수(`<br>` 제외, 약 230자 이하), `#기능 명세`/`#분석` 표시 없이 문단으로 쓴 칸 수(0이어야 한다)를 센다. 넘으면 항목을 줄이거나 나눈다.
2. **반복 캡션 수** — 실행 화면 캡션 중 글자 그대로 같은 문장이 둘 이상이면 모두 삭제하거나 사례별로 다르게 다시 쓴다.
3. **본문 글상자 vs 캡처 출력 일치** — 각 사례의 "실제 출력" 글상자가 같은 사례의 캡처와 같은 문자열인지 확인한다. 안내문이 입력 없이 한 줄에 붙은 글상자와 입력이 줄마다 보이는 캡처가 공존하면 한쪽을 다시 실행해 맞춘다.
4. **보고서 코드 vs 제출 `.c` 서식 일치** — 분석표의 코드 셀은 제출 `.c`에서 주석을 뺀 것과, (있다면) 전체 부록은 제출 `.c` 원문과 비교해 들여쓰기 칸 수, 중괄호 위치(`{`가 같은 줄인지 다음 줄인지), 공백 분포가 일치하는지 확인한다. 어긋나면 제출 `.c`의 서식을 정본으로 보고 보고서 코드를 거기에 맞춘다.
5. **제3자 레이블 사용 횟수** — 본문에서 자기 구현 함수를 "구현 대상 함수", "학생 구현 함수", "본인 구현"으로 부른 횟수를 센다. 0이 아니면 함수 이름이나 "직접 작성한"처럼 1인칭에 가까운 표현으로 바꾼다.
6. **주석 처리** — 표 소스 칸에 남은 `//`·`/*` 수(0이어야 한다)와, 작성자 주석 중 설명 칸에 옮겨지지 않은 것의 수(0이어야 한다. 코드와 달라 옮기지 않은 주석은 검토 기록에 사유)를 센다. 과제4는 0/0이었다.

참고로 과제2 초안은 1이 제공 함수 포함 12/12 같은 틀, 2가 6장 동일 캡션, 3이 "글상자는 입력 생략·캡처는 입력 노출"로 어긋남, 4가 K&R 2-space(제출 `.c`) 대 Allman 4-space(보고서) 혼재, 5가 반복 사용 상태로 넘겼다가 지적됐다. 과제1 최종본은 다섯 항목 모두 임계값 아래였고, 과제3·과제4 재작성본은 1에서 `인자:`를 쓴 제공 함수가 2개·0개, 평균 220자·213자, 표시 없는 칸 0이었다. 추천답 자동 모드도 이 점검을 생략하지 않으며, 임계값 초과 항목과 개인 동기·수업 맥락을 보탤 만한 자리는 **final-edit list**에 "작성자 수정 필요"로 올린다(본문에는 미완성 빈칸을 남기지 않는다). 위 생성 시 비작성 원칙(검산성 쪽수·예시 일치·출제 의도·미발생 예외 경고 배제)과 풀어진 평서문 기준도 넘기기 전에 함께 훑되, 자동으로 항목 삭제·캡션 재작성·서식 재포맷을 수행하지 않는다.

## PDF 확인

- Notion의 기본 글꼴·기본 모드 HTML을 이미지와 함께 내보내고, 다운로드한 실제 HTML을 A4 가로 PDF로 인쇄한다. Notion 자체 PDF 내보내기에 가로 방향 옵션이 있다고 가정하지 않는다. 원본 ZIP·HTML·이미지는 보존하고, 인쇄용 사본의 여백·페이지 나눔·표 폭만 조정한다. 로컬에서 별도로 작성한 HTML을 Notion 내보내기 원본으로 대체하지 않는다. 별도의 A4 가로 표지 제작·병합은 요청된 범위에서 진행한다. 페이지 번호와 브라우저 머리말·꼬리말은 넣지 않는다.
- 내보낸 PDF에서 코드와 분석의 좌우 대응, 텍스트 코드의 선택·추출, 코드 들여쓰기 유지, 코드 글자색, 코드 자동 줄바꿈, 행 분리, 머리행 반복 여부, 제목만 남는 페이지, 넓은 표와 스크린샷의 가독성을 확인한다. 필요하면 정한 간격을 유지하면서 페이지 나누기·열 너비·행 높이를 조정한다.
- Notion 화면, Markdown, 본문 PDF, 병합 PDF, 실제 제출을 서로 다른 상태로 기록한다. 파일을 직접 확인하기 전에는 PDF 양식이나 제출을 통과로 표시하지 않는다.
