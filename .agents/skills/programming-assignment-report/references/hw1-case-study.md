## PDF에서 볼 위치

쪽수는 표지를 포함한 **PDF 파일의 1부터 시작하는 페이지 순서**다. 문서에 인쇄된 페이지 번호가 아니다. 등록 시 확인한 파일은 16쪽 모두 A4 가로 크기다.

| PDF 쪽 | 내용 | 참고할 점 |
|---|---|---|
| 1 | 별도 표지 | 과목·과제·주제·학생 정보를 본문과 분리 |
| 2 | 목차와 구현 목적 | 풀려는 문제와 산출 결과를 먼저 제시 |
| 3–5 | 전역 정의와 입력 함수 분석 | 제공된 선언의 역할, 입력 검증 조건과 오류 흐름 설명 |
| 6–9 | 계산·판정·재귀 탐색·main 분석 | 코드와 기능 명세·동작 원리를 좌우로 대응 |
| 9–10 | 공식 예제1 | 입력·실제 출력·터미널 화면·상태 변화 표·결과 분석 |
| 10–13 | 공식 예제2·3 | 모든 순서가 가능한 경우와 시작할 수 없는 경우를 수치로 설명 |
| 13–16 | 경계값·예외 입력 | 대표 사례 표와 개별 실행 화면·설명 대응 |

전체 페이지 렌더를 축소 모아보기로 검토하고, 7·10·14·16쪽은 개별 렌더로 확인했다. 코드가 텍스트로 추출되고 표와 실행 화면이 존재함을 확인했다. 전 페이지의 모든 줄을 원본 코드와 대조하거나 텍스트 선택을 GUI에서 시험한 검증은 아니다. 특히 7–8쪽처럼 표의 한 행이 다음 페이지로 이어지는 부분도 있으므로, 만점 사례의 페이지 분할을 이상적인 규칙으로 복제하지 않는다. 새 PDF에서는 코드·설명의 대응과 행 분할을 별도로 검사한다.

## 구체적인 설명 사례

아래 인용은 보존 PDF의 짧은 발췌이며, 이어지는 해설은 사례 등록을 위한 설명이다. 후속 과제의 본문에 그대로 붙여 넣는 문구가 아니다.

### 함수 분석: 상태를 바꾸고 되돌리는 이유

PDF 7쪽은 `search_safe_sequence(depth)`의 인자, 반환값, 기저 조건과 자원 회수를 설명한다. 8쪽은 다음처럼 복원 이유를 연결한다.

> 이를 통해 동일한 깊이의 다른 분기 탐색에 영향을 주지 않는다.

실제 코드는 프로세스를 선택할 때 `finish[i] = 1`로 표시하고 `available`에 `allocation[i]`를 더한다. 재귀 호출이 돌아오면 더했던 자원을 빼고 `finish[i] = 0`으로 되돌린다. 설명은 단순히 “값을 더하고 뺀다”에서 끝나지 않고, **다른 후보를 같은 출발 상태에서 검사해야 한다**는 이유까지 다룬다.

자원 회수도 PDF 7쪽에서 다음 관계로 설명한다.

```text
Available - Need + (Allocation + Need) = Available + Allocation
```

후속 과제에서는 해당 코드의 입력·반환값·변경 상태와, 핵심 조건이나 상태 전이가 필요한 이유를 설명한다. 모든 함수에 재귀·복원 설명을 붙이는 양식은 아니다.

### 실행 분석: 실제 값에서 출력까지

PDF 9–10쪽의 공식 예제1은 안전 순서가 1개인 이유를 다음 상태 변화로 보인다. 아래 표는 해당 예제의 요약이다.

| 단계 | Available | 판단·변화 |
|---|---|---|
| 시작 | `(1, 0)` | Need가 `(1, 0)`인 P0은 가능, `(0, 1)`인 P1은 불가 |
| P0 완료 | `(1, 1)` | P0의 Allocation `(0, 1)`을 반환하여 P1도 실행 가능 |
| P1 완료 | `(2, 1)` | P1의 Allocation `(1, 0)`을 반환, 유일한 순서는 P0 → P1 |

PDF 10쪽의 결론은 다음과 같다.

> 따라서 유일하게 가능한 안전 순서는 P0 → P1로 총 1개이다.

이는 출력 숫자를 다시 적는 대신 **입력 상태 → 실행 가능 조건 → 상태 변화 → 관찰한 출력의 이유**를 연결하는 사례다. 새로운 과제에서도 실제 실행과 일치하는 작은 추적을 선택한다.

### 제공 코드와 학생 구현 구분

PDF 3쪽은 `SystemState`, `SearchState`와 파일 범위 `static` 변수의 역할을 설명하면서 제공된 코드임을 밝힌다. [스켈레톤](../../../../과제/과제1/HW1_skeleton.c)에도 이 선언들이 있다. 제공된 구조를 학생이 성능 향상을 위해 새로 설계했다고 쓰지 않으며, 성능 측정 없는 속도 향상 주장으로 확대하지 않는다.

## 실행 근거와 확인 범위

- [기존 실행 기록 after-comments.json](../../../../과제/과제1/검토자료/after-comments.json): 등록 시 보존 C의 SHA-256과 일치했으며, 기록된 사례 18건 모두 `passed: true`였다.
- [검증 스크립트](../../../../과제/과제1/검토자료/verify_hw1.py): 등록 시 제출 C를 다시 빌드·실행하여 **18/18 통과**를 확인했다. 빌드와 JSON 출력은 저장소 밖 임시 디렉터리에 두었다.
- 재실행 환경: macOS 27.0.1 arm64, Apple clang 21.0.0, `-std=c11 -Wall -Wextra -Wpedantic`. 컴파일 진단 출력은 없었다.
- 범위: 기록에 정의된 입력에서 Need 행렬·안전 순서 개수 또는 오류 문구·계산 생략, 종료 코드와 stderr를 검사한다. 모든 가능한 입력, 정수 오버플로, 실제 안전 순서 목록, 다른 운영체제의 동작을 검증한 것은 아니다.
- PDF의 대표 실행 사례는 공식 예제 3건과 경계값·예외 5건이다. 내부 기록의 18건과 보고서에 실은 사례 8건을 구분하며, 이 개수를 후속 과제의 요구로 재사용하지 않는다.
