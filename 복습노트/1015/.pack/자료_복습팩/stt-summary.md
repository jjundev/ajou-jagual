## 1. 큐 복습과 선형 배열 큐의 한계 (Part 01, 시간 정보 없음)

**핵심 내용**: 스택은 LIFO, 큐는 FIFO다(S6 p2). 큐는 먼저 들어온 데이터를 먼저 꺼내므로 도착 순서를 지켜야 하는 대기열과 서로 다른 처리 속도 사이의 버퍼에 적합하다(S6 p4). 큐의 삽입은 후단 `rear`, 삭제는 전단 `front`에서 일어난다(S6 p3). 배열을 선형으로만 쓰면 삭제 뒤 앞쪽에 빈칸이 있어도 `rear`가 끝에 도달하면 새 항목을 넣을 수 없다. 계속 삽입하려면 기존 요소를 옮겨야 한다. 배열을 논리적으로 이어 붙인 원형 큐가 이를 해결한다(S6 p5). 배열 자체가 물리적으로 원형으로 변하는 것은 아니다.

**비유와 일화**: 빈자리가 생겼다고 새 고객을 줄 맨 앞에 세우면 FIFO의 공정성이 깨진다는 매표소 비유. 배열 구현을 고를 때도 희소 행렬처럼 표현 방식까지 고민해야 한다고 설명했다. 카르노 맵과 시각화 이야기는 구현 과정을 눈으로 확인하면 판단하기 쉬워진다는 맥락이었다. [슬라이드 외]

**학생과의 대화**: 특정 학생의 발언은 전사되지 않았다.

**강조 발언**: “그래서 비주얼라이제이션(visualization), 소프트웨어 이제 뭐 프로그래밍하고 이럴 때는 사실 시각화하는 툴들이 너무 중요하게 작용을 합니다.” (Part 01, 시간 정보 없음) 논리회로 K-map 시험에서 항을 더 묶을 수 있는지 확인하기 쉽다는 경험담은 시각화의 동기를 설명한 것으로, 이번 시험 범위 안내는 아니다.

## 2. 원형 큐의 상태와 연산 (Part 01–02, 시간 정보 없음)

**핵심 내용**: `front`는 첫 요소 바로 앞의 인덱스, `rear`는 마지막 요소의 인덱스다(S6 p6). 초기 공백은 `front == rear`이고, A를 넣으면 `rear`를 한 칸 옮겨 그 자리에 저장한다. B를 넣어도 `front`는 그대로다. A를 빼면 `front`를 한 칸 옮긴 뒤 그 위치의 A를 반환한다(S6 p7, p9). A·B를 차례로 넣고 둘 다 빼면 두 인덱스가 2에서 다시 같아진다. 공백을 뜻하는 인덱스가 반드시 0일 필요는 없다.

크기가 $M$인 배열에서 인덱스는 `(index + 1) % M`으로 회전한다. 공백 조건은 `front == rear`, 포화 조건은 `(rear + 1) % M == front`다. 공백과 포화를 구별하려고 물리적 칸 하나를 항상 비워 실제 저장 용량은 $M-1$개다(S6 p8–9). 8칸 예시에서는 7 다음이 0이 된다. `enqueue`는 포화를 검사하고 `rear`를 옮겨 저장하며, `dequeue`는 공백을 검사하고 `front`를 옮긴 뒤 해당 요소를 돌려준다. 각 연산은 인덱스 갱신과 배열 접근만 하므로 $O(1)$이다.

슬라이드 S6 p9의 코드 조각(표기 그대로):

```c
return (q->front == q->rear);
q->rear = (q->rear+1) % MAX_QUEUE_SIZE;
q->queue[q->rear] = item;
q->front = (q->front+1) % MAX_QUEUE_SIZE;
return q->queue[q->front];
```

**비유와 일화**: 자리가 비는 원탁에서 머리·꼬리의 위치만 옮긴다는 비유. [슬라이드 외]

**학생과의 대화**: 전사된 개별 질문은 없다. 교수가 “왜 8개의 방 중 하나를 비우는가”를 질문 형태로 제시하고 공백과 포화의 구별을 설명했다.

🕳️ 미룬 유도: Part 01에서 `front` 앞의 한 칸을 “왜 비우는지는 뒤에 설명”한다고 했고, Part 02에서 공백·포화 구별로 설명을 마쳤다.

## 3. 연결 큐와 덱의 정의·연산 (Part 02–03, 시간 정보 없음)

**핵심 내용**: 크기를 미리 정할 수 있는 버퍼에는 배열 원형 큐를, 크기를 미리 정하기 어려운 경우에는 연결 큐를 고려한다고 설명했다. 연결 큐는 단순 연결 리스트와 `front`·`rear` 포인터를 쓰며, 비면 두 포인터가 `NULL`이다(S6 p10). 삽입은 항상 `rear` 다음, 삭제는 항상 `front`에서 한다(S6 p11). 삭제할 노드를 먼저 보관하고 연결을 다음 노드로 옮긴 후 해제해야 나머지 노드에 접근할 수 있다. 일반적인 끝 포인터 유지 방식에서 두 연산은 $O(1)$이다.

덱(`deque`, double-ended queue)은 앞뒤 모두에서 삽입과 삭제가 가능하다(S6 p12). `add_front`, `add_rear`, `delete_front`, `delete_rear`, `get_front`, `get_rear`를 소개했다(S6 p13). 시연 순서는 `add_front(A)` → `add_rear(B)` → `add_front(C)` → `add_rear(D)` → `delete_front()` → `delete_rear()`이며, 상태는 `[A]` → `[A,B]` → `[C,A,B]` → `[C,A,B,D]` → `[A,B,D]` → `[A,B]`다(S6 p14). 슬라이드의 구현은 `head`·`tail`을 갖는 이중 연결 리스트다(S6 p15). 교수는 전단 삽입 때 배열의 요소 이동을 피하기 위해 연결 리스트 구현을 택한다고 설명했다. 덱 자체가 배열로 구현 불가능하다는 뜻은 아니다.

**비유와 일화**: 연결 큐에서 노드를 먼저 해제하면 남은 노드가 “낙동강 오리알”이 된다는 표현으로 포인터 갱신 순서를 강조했다. [슬라이드 외]

**학생과의 대화**: 전사된 개별 질문은 없다.

**강조 발언**: “front가 얘를 가리키게 한 다음에 얘를 삭제해 줘야 돼요. 그렇죠? 그 순서가 매우 중요합니다.” (Part 02, 시간 정보 없음)

## 4. 이중 연결 덱의 포인터 갱신과 삭제 (Part 03–04, 시간 정보 없음)

**핵심 내용**: 노드는 `data`, 왼쪽 연결 `llink`, 오른쪽 연결 `rlink`를 갖는다(S6 p15). `add_rear`에서는 새 노드의 `llink`를 기존 `tail`에 연결하고, 빈 덱이면 `head`를 새 노드에 두며 그렇지 않으면 이전 `tail->rlink`를 새 노드에 둔다. 마지막에 `tail`을 새 노드로 옮긴다(S6 p16). `add_front`는 대칭적으로 새 노드의 `rlink`를 기존 `head`에 연결한다. 새 링크를 확보하기 전에 기존 끝 포인터를 바꾸면 노드를 잃을 수 있다고 강조했다.

`delete_front`는 공백을 검사하고 `removed_node = dq->head`로 삭제 대상을 보존한다. 반환할 `item`을 읽은 다음 `head`를 `head->rlink`로 옮기고 `removed_node`를 해제한다. 새 `head`가 `NULL`이면 `tail`도 `NULL`, 아니면 `head->llink = NULL`로 만든다(S6 p17). 한 노드만 있던 경우가 별도 분기인 이유다. 연결만 고치는 끝단 연산은 $O(1)$이다.

슬라이드 S6 p16–17의 코드 조각(표기 그대로):

```c
DlistNode *new_node = create_node(NULL, item, dq->head);
removed_node = dq->head;   // 삭제할노드
item = removed_node->data; // 데이터추출
dq->head = dq->head->rlink; // 헤드포인터변경
free(removed_node);
```

**비유와 일화**: 새 노드가 먼저 양쪽으로 “팔을 뻗어” 이웃을 잡은 뒤 끝 포인터를 옮긴다는 비유. 하나의 노드를 여러 포인터가 동시에 가리킬 수 있다는 설명에도 문을 여러 사람이 가리킬 수 있다는 비유를 썼다. [슬라이드 외]

**학생과의 대화·시험 강조**: `create_node`의 본문이 없으면 문제를 풀 수 없다는 학생들의 반응을 소개했다. 교수는 `create_node(dq->tail, item, NULL)`의 인자 순서로 `llink`, `data`, `rlink`를 추론할 수 있어야 한다고 말했다. 원문: “가끔 이제 뭐 이런 거 시험 문제 내면 학생들이 그래요. create_node가 뭔지도 알려 주셔야죠” 및 “이 create_node의 바디를 보여 주지 않더라도 여러분들이 추정할 수 있어야 돼요.” (Part 03, 시간 정보 없음)

## 5. 생산자·소비자 버퍼 (Part 04, 시간 정보 없음)

**핵심 내용**: 큐는 생산과 소비 속도가 다른 두 프로세스 사이에서 입력 순서를 지키며 데이터를 잠시 저장한다(S6 p18). 프린터와 CPU, 키보드와 CPU가 예시다. 생산자는 버퍼가 가득 차지 않았을 때 `enqueue`, 소비자는 비지 않았을 때 `dequeue`한다(S6 p19). 같은 버퍼에 동시에 접근할 때 `lock`/`unlock`으로 한쪽이 갱신하는 동안 다른 쪽의 접근을 조정한다는 개념을 설명했다. `while(1)`은 반복 실행을 뜻한다. 슬라이드 S6 p19는 개념용 의사코드로, `lock(buffer) == SUCCESS`의 조건 표기와 실제 잠금 성공/실패 의미는 별도 확인이 필요하다. 강의에서 이 코드의 동시성 보증을 검증한 것은 아니다.

**비유와 일화**: 버퍼 잠금은 열쇠를 가진 쪽이 잠시 주도권을 갖고 작업 후 열쇠를 돌려주는 것에 비유했다. 은행 제출, 원서 제출, 네트워크 패킷 충돌 등의 사례는 동시 접근에 대한 동기 설명이다. [슬라이드 외]

**학생과의 대화**: 전사된 개별 질문은 없다.

## 6. 은행 대기열 시뮬레이션과 시험 안내 (Part 04–05, 시간 정보 없음)

**핵심 내용**: 서버 한 명이 고객을 도착 순서대로 처리하는 큐잉 모델로 평균 대기 시간을 계산한다(S6 p20). 교수의 구두 추적에서 시각 1에 고객 0이 도착해 3분 서비스를 즉시 시작하고 대기는 0분이다. 시각 2에 고객 1(서비스 5분), 시각 3에 고객 2(서비스 3분)가 도착해 큐에 쌓인다. 시각 4에 고객 1이 서비스를 시작하여 $4-2=2$분 기다렸다. 시각 4에 고객 3도 도착한다. 시각 9까지 고객 1의 5분 서비스가 진행되며 다음 고객은 대기한다. 제시한 실행 결과는 10분까지 서비스받은 고객 3명, 대기 시간 합계 $0+2+6=8$분, 평균 $8/3\approx2.67$분이다. 이 수치를 통해 점원 수를 늘릴지 판단하는 예를 들었다. 전사만으로 세 번째 고객의 정확한 서비스 시작·완료 처리 시점과 시각 10의 대기 고객 4명을 재구성할 수 없으므로 이 부분은 구두 결과로만 기록한다.

S6 p21–22에서는 `clock`을 1씩 늘리는 반복 루프, 무작위 도착 여부와 서비스 시간, 고객의 도착 시간 기록, 현재 `service_time` 감소 또는 큐의 다음 고객 시작을 설명했다. 종료 시각 `duration`에서 `print_stat()`로 통계를 출력한다. 운영체제의 프로세스 처리나 아이스크림 가게 대기열로도 모델을 옮길 수 있다고 언급했다. [슬라이드 외]

슬라이드 S6 p22의 코드 조각(표기 그대로):

```c
while(clock < duration){
clock++;
if (is_customer_arrived()) {
insert_customer(clock);
}
if (service_time > 0)
service_time--;
else {
service_time = remove_customer();
}
}
print_stat();
```

**비유와 일화**: 은행 창구 하나를 서버, 고객을 처리할 작업, 줄을 큐로 놓아 시간마다 큐가 어떻게 변하는지 따라갔다. 처리 시간이 과하면 점원 수를 늘린다는 운영 판단과 연결했다.

**학생과의 대화**: 마지막 질문을 받았지만 질문자의 직접 발화는 전사되어 있지 않다. 교수가 여러 학생에게서 받은 연습문제 출제 관련 질문을 답했다.

**시험 강조 발언**: “교재에 있는 연습문제 조금 좀 바꿔서 냈고요, 똑같이 낸 것도 있어요.” “강의 자료를 충분히 이해했으면 풀 수 있는 정도는 돼요.” “강의 자료에 있는 코드들도 조금 보면 좋을 거 같고.” (Part 05, 시간 정보 없음)

## 말실수 정정

- 원형 큐 설명 초반에 `front`가 “첫 번째 요소”를 가리킨다는 표현이 있지만, S6 p6·p9의 실제 구현과 뒤의 설명에서는 **첫 번째 요소 하나 앞**을 가리킨다. 복습 노트에는 후자를 쓴다.
- 원형 큐의 삭제를 “front에 있는 애를 꺼내고 나서 front를 증가”한다고 말한 대목은 순서가 뒤집힌 구두 설명이다. S6 p9 코드에서는 `front`를 먼저 증가시킨 다음 `q->queue[q->front]`를 반환한다.
- “덱은 array로 구현하지 않습니다”는 이 강의의 이중 연결 리스트 구현 선택을 강조한 말로 다룬다. 덱의 정의상 배열 구현이 불가능한 것은 아니다.
- “double linked list”는 일반적인 용어로 **doubly linked list(이중 연결 리스트)**다.
- 전사의 “arrival prob”는 S6 p21에서 `arrival_prov`로 추출되어 있다. 변수 철자는 슬라이드·원본 코드 재확인 전까지 확정하지 않는다.
- 버퍼 S6 p19의 `while( lock(buffer) == SUCCESS ) ;` 조건은 강의의 “잠금에 성공하면 작업”이라는 설명과 맞지 않아 보인다. 슬라이드 표기를 그대로 인용하고, 실제 동시성 코드로 재사용하기 전 검증이 필요하다.
