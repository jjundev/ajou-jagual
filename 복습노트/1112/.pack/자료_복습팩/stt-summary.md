## 1. 힙의 용도: 스토어 관점과 서랍 정리 (Part 01)

**핵심 내용**
- (S8 p14 마지막 항목) 힙 정렬이 가장 유용한 경우는 전체 자료를 정렬할 때가 아니라 **가장 큰 값 몇 개만 필요할 때**다.
- 힙은 데이터가 들어올 때 힙으로 만들면서 저장하는 시간이 든다. 100개든 1000개든 그중 10% 정도만 꺼내 쓸 일이 생기고, 하나를 꺼내면(루트 삭제) 말단 노드가 올라가 내려오면서 다시 힙을 만든다. [슬라이드 외]
- 로드·스토어 관점: 힙 구조를 계속 유지하는 것이 **스토어 관점**이다. 저장할 때 공을 들여 두면 꺼낼 때 빠르다. [슬라이드 외]
- 힙으로 정렬한다는 컨셉은 힙 정렬뿐 아니라 "저장을 체계적으로 하고 싶을 때"도 쓰인다. 정렬은 디폴트 알고리즘으로 생각하라. [슬라이드 외]

**비유와 일화**
- **로드·스토어 85%**: 교수님이 RISC 프로세서 컨트롤러 블록을 설계하며 명령어를 분석해 보니 85%가 로드(메모리에서 데이터를 가져옴)·스토어(계산한 값을 메모리 몇 번지에 write), ALU 명령어는 15% 이내였다. → "메모리가 여왕벌이구나", "CPU는 일벌". 이것이 소프트웨어에도 해당된다(자료를 어떻게 저장하느냐가 핵심).
- **서랍 정리**: 서랍을 깨끗이 정리해 두면 나중에 꺼낼 때 엄청 빠르다. 100개 아이템을 다 꺼내려고 정리하는 게 아니라, 한 번에 두세 개를 빨리 꺼내려고 정리한다. → 힙 = 스토어에 노력을 기울여 상위 몇 개를 빨리 꺼내는 구조.
- **말단 사원**(1109 비유 재사용): 루트를 빼면 말단 사원이 올라가서 내려오면서 다시 힙을 만든다.

**학생과의 대화**
- 없음(녹음 구간).

**강조 발언**
- "힙(heap) 정렬이 최대로 유용한 경우는 전체 자료를 다 뒤지는 게 아니라 상위 몇 개만 뒤지는 일이라고 얘기를 했잖아요?" (Part 01)
- "로드, 스토어 관점에서 힙이라는 자료구조를 계속 유지하는 게 스토어 관점인 거예요." (Part 01)
- "정렬이라고 하는 챕터에 들어가면 이제 여러분들한테 강조를 하겠지만, 이 세상의 정렬이라는 알고리즘은 그냥 디폴트(default) 알고리즘이다, 이렇게 생각을 하세요." (Part 01)

## 2. 힙 정렬 프로그램 heap_sort (Part 01)

**핵심 내용**
- 슬라이드 S8 p15 코드(글자 그대로):

```c
// 우선순위큐인히프를이용한정렬
void heap_sort(element a[], int n)
{
int i;
HeapType h;
init(&h);
for(i=0;i<n;i++){
insert_max_heap(&h, a[i]);
}
for(i=(n-1);i>=0;i--){
a[i] = delete_max_heap(&h);
}
}
void init(HeapType *h)
{
h -> heap_size = 0;
}
typedef struct {
int key;
} element;
typedef struct{
element heap[MAX_ELEMENT];
int heap_size;
} HeapType;
```

- 슬라이드 주석: "오름차순으로 a[i] 정렬".
- 동작(구두): `init` 으로 초기화 → 첫 for 루프는 `i` 를 0부터 `n` 보다 작을 때까지, 데이터가 하나씩 `n` 개까지 들어올 때마다 `insert_max_heap` 을 돌린다. → 그다음 두 번째 for 루프는 `i` 를 `n - 1` 부터 0 이상일 때까지, 말단을 하나씩 올리면서 `delete_max_heap` 이 루트를 리턴한다.
- 결론: insert 를 $n$ 번, delete 를 $n$ 번 돌리면 저절로 정렬된다. 각 연산 $O(\log n)$ × $n$ 개 → 전체 $O(n\log n)$ (S8 p14).
- [슬라이드 외 보충] 최대 힙에서 가장 큰 값이 먼저 나오므로 `a[n-1]` 부터 거꾸로 채워 결과가 오름차순이 된다(교수님은 인덱스 방향의 이유를 따로 설명하지 않음).

**비유와 일화**
- "말단 사원을 하나씩 올리면서" — delete 시 마지막 노드를 루트로 올리는 downheap.

**학생과의 대화**
- 없음.

**강조 발언**
- "이렇게 해서 insert 돌리고 n번 돌리고, delete n번 돌리면 저절로 소팅이 되더라라는 겁니다." (Part 01)

## 3. 힙 응용 2: 이산 이벤트 시뮬레이션 (Part 01–02)

**핵심 내용**
- 이산 사건(discrete event): 시간에 따라 이벤트가 일어나는데 연속(continuous)이 아니라 "요 타임에 고객이 들어왔다, 그다음 타임에 아이스크림을 주문했다"처럼 구별되는 시점에 딱딱 일어나는 것. 5초 다음 0.0002초처럼 간격이 작아도 구별할 수 있으면 discrete.
- 시뮬레이션에는 큐(queue)가 많이 쓰인다. 줄 서기 = 들어온 순서대로 처리 → 현실의 줄은 큐로 모델링.
- 그런데 실제 아이스크림 가게에는 이벤트가 여러 가지다(S8 p16: 도착 arrival, 주문 order, 떠남 leave): 손님 도착, 주문, 들고 나가기, 착석해서 먹기, 자리부터 잡느라 줄에서 이탈했다 돌아오기, take-out 이라 우선순위가 빨라지기, 자리가 없어 그냥 나가기. [구체 사례 일부 슬라이드 외]
- 하나의 큐로는 다 표현할 수 없고, 여러 큐로 하면 큐끼리 어떻게 연관시킬지가 문제. → 들어온 순서를 기본으로 지키면서 우선순위를 줄 수 있는 **우선순위 큐(priority queue)** 를 쓰면 우선순위가 있는 다양한 이벤트를 다룰 수 있다.
- 슬라이드 p16 의 의자 수 규칙(남은 의자 수 > 도착 인원이면 의자 수 감소, 적으면 주문 없이 나감, leave 수만큼 의자 수 증가)은 구두로 자세히 짚지 않았다.

🕳️ 미룬 유도: "자 실제 코드는 여러분들 그 책에 있는 코드를 보고 한번 해보세요." (Part 02) — 시뮬레이션 코드(슬라이드 표기 "(p328)")는 수업에서 다루지 않고 교재로 미뤘다.

**비유와 일화**
- 아이스크림 가게 줄: 줄 서기 = 큐, take-out 손님을 맨 앞으로 보내기 = 우선순위.
- 이산수학: 컴퓨터 분야의 핵심 수학(전자공학의 공업수학 2 에 해당), 디지털이 아날로그보다 쉽듯 공업수학보다 쉽다. 대학원에 "이산 사건 시스템" 과목도 있다.

**학생과의 대화**
- 교수님이 "이산수학 수강했던 사람" 손을 들어 보라고 했고, 몇 명뿐이었다(옛날엔 필수였다고 언급).

**강조 발언**
- "사실 이산수학이요, 컴퓨터 분야에서는 핵심적인 수학입니다." (Part 01)
- "요런 이산 이벤트 시뮬레이션에 priority queue를 쓰면 다양한 이벤트들, 우선순위가 있는 이벤트들을 다룰 수 있다 이렇게 생각하시면 됩니다." (Part 02)

## 4. 힙 응용 3: 허프만 코드 (Part 02–03)

**핵심 내용**
- 코드(code)의 원래 뜻은 암호, 즉 사람들끼리 정한 약속. 예: ASCII 에서 대문자 A 를 65 로 정한 것 — 이유 없이 그냥 정한 것. 1의 보수·2의 보수·부호와 크기도 코드. [슬라이드 외]
- 이진 트리는 각 글자의 빈도가 알려진 메시지 압축법에도 쓰인다 → **허프만 코딩 트리(Huffman coding tree)** (S8 p17).
- 빈도표 예(p17): A 80, B 16, C 32, … Z 1.
- **etnis 예제**: e 15, t 12, n 8, i 6, s 4 → 총 $15+12+8+6+4 = 45$ 글자.
  - 5개 글자 → 2비트(4개까지)로는 부족, 3비트($2^3 = 8$개)로 표현(e = 000, t = 001, n = 010 …) → $45 \times 3 = 135$ bits.
  - 허프만 코딩 트리를 쓰면 100 bits.
- **트리 만들기(교수님 구두 순서)**:
  1. 빈도가 작은 것부터 늘어놓는다(오름차순 단말 노드화): 4, 6, 8, 12, 15.
  2. 가장 작은 두 개 4 + 6 → 10.
  3. 남은 것 10, 8, 12, 15 → 10 + 8 = 18 (교수님은 8 + 12 = 20 과 비교해 18 이 더 작다고 확인).
  4. 남은 것 18, 12, 15 → 18 + 12 = 30 과 12 + 15 = 27 을 비교해 12 + 15 = 27.
  5. 남은 18, 27 → 45 (= 총 빈도 합).
- **코드 배정**: 왼쪽 가지 0, 오른쪽 가지 1(반대로 해도 상관없음). 교수님 구두: 빈도 4 → 1,1,1 / 6 → 1,1,0 / 8 → 1,0 / 12 → 0,1 / 15 → 0,0.
- **결과표(S8 p19)**:

| 글자 | 비트 코드 | 빈도 | 비트 수 |
|---|---|---|---|
| e | 00 | 15 | 30 |
| t | 01 | 12 | 24 |
| n | 10 | 8 | 16 |
| i | 110 | 6 | 18 |
| s | 111 | 4 | 12 |

  $15\cdot2+12\cdot2+8\cdot2+6\cdot3+4\cdot3 = 100$ bits. 135 bits 에서 35 bits 감소($35/135 \approx 25.9\%$, 슬라이드·교수님 표현은 "26%").
- 원리: 빈도가 가장 작은 글자들을 말단(가장 깊은 레벨)에 내려놓아 경로가 길어진다 → 가장 긴 비트 수가 가장 작은 빈도에 배정된다. 어떤 글자는 3비트, 어떤 글자는 2비트.

**비유와 일화**
- 코드 = 암호: "야, 너랑 나랑 숫자로 65라고 하자, A를." 이유를 묻지 않는 약속.
- 과거에 이 챕터를 배운 학생이 융캡(STT 표기 그대로)에서 압축 코드를 만들며 허프만 코드로 개선한 결과를 보여준 적이 있다.

**학생과의 대화**
- 없음.

**강조 발언**
- "근데 주의해야 될 게 뭐냐면 무조건 쟤랑 보는 게 아니라 얘네 둘이 봐서 작을지도 확인을 해야 돼요." (Part 02)
- "표현하는 비트 수가 가장 긴 애가 가장 작은 빈도를 가진 애한테 할당이 되는 겁니다." (Part 02)
- "그래서 135비트를 100비트로 했기 때문에 26% 줄일 수 있었다라고 얘기하는 겁니다." (Part 03)
- "얘 가만히 보면 힙(heap)이에요. 무조건 힙을 만들 수밖에 없습니다." (Part 03) — 정정 필요, 아래 「말실수 정정」 참고.

  - $O(\log n)$ (삽입·삭제 1회), $O(n\log n)$ (힙 정렬 전체)
