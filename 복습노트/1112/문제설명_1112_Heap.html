핵심 조건과 구할 것

100글자 문서(A~H 빈도 표)에서 1) 고정 길이 코드의 글자당·총 비트 수와 2) 허프만 압축 결과(총 비트·트리·코드)를 구해요.

  • 원문 오기 주의: 문제 1)은 “7가지”라고 적었으나 표의 글자는 A~H 8종이에요(채점 답안에서도 8로 정정; 7로 보든 8로 보든 3 bit는 같아요).
  • 코드 규칙: 트리 가지는 left 0, right 1로 붙이고, 어느 자식을 왼쪽에 둘지는 정해지지 않았어요.

이 문제를 봤을 때 떠올릴 개념과 공식

문제 단서꺼낼 도구·공식이유와 조건
문자당 ( ) bit / 100개 고정 길이 코드: $2^b \ge k$ 인 최소 정수 $b$, 총 비트 $N \times b$ $b$ 비트로 최대 $2^b$ 종류를 구별하므로 $k=8$ 에 맞춰 $b$ 를 정해요(정리노트).
허프만 코딩 + 빈도 표 최소 힙(min heap) 기반 반복 병합 자주 나오는 글자를 위로, 드문 글자를 아래로 두려면 매 단계 남은 전체 중 최소 둘을 묶어 다시 넣어야 해요(정리노트).
left 0, right 1 / 총 bit 총 비트 $= \sum(\text{빈도}\times\text{코드 길이})$ 각 글자의 코드 길이는 루트에서 단말까지의 깊이예요(정리노트).

종이에 쓰는 실제 첫 줄

1) 글자 8종: 2^2 = 4 < 8 <= 2^3 = 8  →  3 bit/글자,  100 × 3 = 300 bit
2) 빈도 정렬: D 1, H 2, E 5, B 8, G 9, A 15, C 20, F 40  →  1단계: D 1 + H 2 = 3

왜 이렇게 푸는지 함께 따라가요

1) 고정 길이 코드

  • 총 비트를 ‘코드 길이의 합’으로 계산하거나 “7가지”를 그대로 믿으면: 길이 합($1+3+3+3+4+5+6+6=31$)은 100글자 문서의 총 비트가 아니에요. 또 원문 “7가지”만 보고 표를 세지 않으면 다른 문제에서 $2^b$ 경계를 놓칠 수 있어요.

  3. 코드 표를 다 적기 전에 병합 표의 합만 더해서 총 비트 247을 검산해 보세요.

떠올릴 개념·공식

고정 길이 $2^b \ge k$ (원문 “7가지” 오기→실제 8종, 모두 $b=3$). 허프만은 남은 전체 중 최소 둘 병합(최소 힙). 총 비트 $= \sum(\text{빈도}\times\text{길이}) =$ 내부 노드 합.

첫 줄

8종 → 3 bit, 300 bit. 빈도 정렬 D 1, H 2, E 5, B 8, G 9, A 15, C 20, F 40에서 1+2=3부터 시작.

핵심 판단

검산

빈도 합 100 = 루트, 내부 노드 합 $3+8+16+24+36+60+100 = 247$, 접두어 충돌 없음.

핵심 조건과 구할 것

보기 4개 중 히프 정렬(heap sort)이 특히 유용한 경우 1개를 고르는 긍정형 단일 선택 문항이에요.

  • 단순히 “히프 정렬로 정렬이 가능한가”가 아니라, 다른 정렬보다 히프를 쓸 뚜렷한 장점이 있는지를 따져요.

이 문제를 봤을 때 떠올릴 개념과 공식

문제 단서꺼낼 도구·성질이유와 조건
특히 유용한 경우 부분 정렬(상위·하위 $k$ 개 추출): 힙 구성 + $k$ 번 삭제 루트 삭제 한 번이 $O(\log n)$ 이라 전체 $n$ 개를 다 빼지 않고 필요한 $k$ 개만 꺼내고 멈출 수 있어요(S8 p14, 정리노트).
나머지 보기 비교 입력 무관 $O(n \log n)$ / 배열 내 요소 복사 이동 초기 입력 순서(역순 등)에 따른 이득이 없고, upheap·downheap마다 레코드를 여러 번 옮겨요.

종이에 쓰는 실제 첫 줄

① 100개 중 20개만 → 최소 히프 구성 후 삭제 20번만 수행(나머지 80개 미정렬 가능)

왜 이렇게 푸는지 함께 따라가요

  • ① 데이터 100개 중에서 오름차순으로 20개만 뽑고자 할 때 [정답]: 최소 히프에 100개를 넣고 루트 삭제를 20번만 수행하면 가장 작은 20개가 오름차순으로 나와요. 나머지 80개를 정렬하는 비용을 아낄 수 있어 S8 p14에서 강조한 “몇 개만 필요할 때”에 딱 맞아요.
  • ② 비교적 데이터의 개수가 적을 때 [소거]: 원소 수가 적으면 단순 삽입 정렬 등이 상수 비용이 작아 더 빨라요. 히프 구성·유지 오버헤드를 감수할 이유가 없어요.
  • ③ 정렬의 대상이 되는 레코드의 크기가 클 때 [소거]: upheap·downheap 과정에서 요소를 여러 번 복사·이동해야 하므로, 레코드 덩치가 클수록 이동 비용이 커져 오히려 불리해요.
  • ④ 데이터가 역순으로 정렬되어 있을 때 [소거]: 히프 정렬은 입력 순서와 무관하게 넣기 $n$번·빼기 $n$번($O(n\log n)$)이 걸리므로, 역순 입력이라고 특별히 빨라지지 않아요.

완성 답과 검산

완성 답: ① 데이터 100개 중에서 오름차순으로 20개만 뽑고자 할 때 (교과서 9장 4번 356쪽 인쇄 정답 없음 — 공식 답 미확인).

  • 연산 횟수 비교: 100개 전체 삭제는 $100$번의 downheap($O(100\log 100)$)이 들지만, ①은 $20$번만 삭제해 삭제 비용이 $1/5$로 줄어요.
  • 강의 자료 일치: 강의 S8 p14의 “전체 자료를 정렬하는 것이 아니라 가장 큰 값 몇 개만 필요할 때(최소 히프면 작은 값 몇 개)”와 일치하고, 오답 ②·③·④는 각각 상수 비용·레코드 이동·입력 무관성 측면에서 장점이 없거나 불리함이 확인돼요.

오해하기 쉬운 이유와 반례

  • “역순 데이터”를 보고 ④를 고르는 습관: 역순은 퀵 정렬(단순 피벗)이나 삽입 정렬에서 최악 성능이 나는 특수 케이스이지만, 히프 정렬은 입력 배열의 초기 순서와 무관하게 $O(n\log n)$이므로 역순에서 특별히 유리할 근거가 없어요.
  • “크기가 클 때”를 데이터 개수로 착각해 ③을 고르는 실수: ③의 ‘레코드의 크기’는 원소 개수 $n$이 아니라 레코드 하나가 차지하는 바이트 크기예요. 큰 구조체를 배열로 계속 복사 이동시키면 오히려 성능이 떨어져요.

해설을 닫고 스스로 확인해요

  1. 선택지에서 “전체 중 상위·하위 $k$개만”이라는 문구를 보면 → 히프 삭제 $k$번 후 조기 종료 이점을 먼저 떠올리세요.
  2. 만약 문제가 “가장 큰 값 5개만 내림차순으로 뽑을 때”라면 최소 히프와 최대 히프 중 무엇을 써야 할까요?

떠올릴 개념·공식

S8 p14: 히프 정렬은 전체 정렬보다 상위·하위 $k$개만 필요할 때 가장 유용해요(삭제 1회 $O(\log n)$ × $k$번만 수행).

첫 줄

① 일부(20개)만 필요 → 삭제 20번 후 종료 가능.

핵심 판단

① 정답. ② 소규모는 단순 정렬이 유리, ③ 큰 레코드는 복사 이동 비용 증가로 불리, ④ 입력 순서와 무관한 $O(n\log n)$.

검산

최대 힙 h는 h.heap[1]부터 h.heap[h.heap_size]까지 요소를 담아요. 0번 칸은 쓰지 않아요. MAX_ELEMENT는 200이에요. 아래 첫 코드는 원래 예제 코드 그대로예요. 코드에서는 typedef가 함수 뒤에 있고, heap_sort가 아래에서 정의되는 init·insert_max_heap·delete_max_heap을 먼저 불러요. 두 typedef와 이 세 함수의 원형(선언)이 heap_sort보다 앞에 있다고 보고 풀어요.

// 우선순위 큐인 히프를 이용한 정렬
void heap_sort(element a[], int n)
{
    int i;
    HeapType h;
    init(&h);
    for(i=0;i<n;i++){
        insert_max_heap(&h, a[i]);
    }
    for(i=(n-1);i>=0;i--){
        a[i] = delete_max_heap(&h);
    }
}
void init(HeapType *h)
{
    h -> heap_size = 0;
}
typedef struct {
    int key;
} element;
typedef struct{
    element heap[MAX_ELEMENT];
    int heap_size;
} HeapType;

두 번째 코드는 이 문제를 위해 쓴 삽입·삭제 함수예요. insert_max_heap은 새 요소를 맨 끝 칸에 놓고 부모보다 크면 올려요. delete_max_heap은 루트를 돌려주고, 마지막 요소를 루트 자리에서부터 큰 자식과 비교하며 내려요. 오른쪽 자식이 없으면 왼쪽 자식과 비교해요.

/* 이 문제를 위해 쓴 자체 코드: 삽입(upheap), 삭제(downheap) */
void insert_max_heap(HeapType *h, element item) {
    int i = ++(h->heap_size);
    while ((i != 1) && (item.key > h->heap[i / 2].key)) {
        h->heap[i] = h->heap[i / 2];
        i /= 2;
    }
    h->heap[i] = item;
}
element delete_max_heap(HeapType *h) {
    int parent = 1, child = 2;
    element item = h->heap[1], temp = h->heap[(h->heap_size)--];
    while (child <= h->heap_size) {
        if ((child < h->heap_size) &&
            (h->heap[child].key < h->heap[child + 1].key)) child++;
        if (temp.key >= h->heap[child].key) break;
        h->heap[parent] = h->heap[child];
        parent = child; child *= 2;
    }
    h->heap[parent] = temp;
    return item;
}

a[]의 key가 차례로 1, 23, 7, 8, 20이고 n = 5로 heap_sort(a, 5)를 불러요.

이 문제를 봤을 때 떠올릴 개념과 공식

문제 단서꺼낼 도구·코드 규칙이유와 조건
(a) 첫 루프: insert_max_heap 1-indexed upheap: i = ++heap_size, 부모 i / 2 새 값이 부모보다 크면 부모를 아래로 밀고 올라가며 최대 힙 불변식을 유지해요(1109 정리노트).
(b) 둘째 루프: delete_max_heap downheap: child < heap_size 일 때만 오른쪽 비교 루트 반환 후 끝 원소 temp를 내리되, 줄어든 heap_size 경계 밖을 읽지 않도록 해요(1109 정리노트).
(c) i = n-1부터 0까지 + 복잡도 최대 힙 추출 순서 + $2n \cdot O(\log n) = O(n \log n)$ 최대 힙은 큰 값부터 나오므로 맨 뒤부터 채워야 오름차순이 되고, 두 루프는 순차 실행이에요(정리노트).

(b) 완성 답: i=4: 23(20 8 7 1) → i=3: 20(8 1 7) → i=2: 8(7 1) → i=1: 7(1) → i=0: 1(빈 힙), 최종 a[] = [1, 7, 8, 20, 23].

검산: C11 실행 시 0번 칸과 힙 밖을 더미 값(0xABABABAB)으로 채워도 결과나 남은 힙에 섞이지 않아 범위 밖 읽기가 없음을 확인했고, 최종 a[]가 입력 5개의 오름차순 정렬과 일치해요.

(c) 완성 답: 최대 힙은 큰 값부터 나오므로 a[n-1]부터 채워 오름차순 완성, 시간 복잡도 $O(n \log n)$.

검산(루프 불변식 및 경계): 각 반복 후 a[i..n-1]에는 가장 큰 $n-i$개가 오름차순으로 놓이고 힙에는 나머지 $i$개가 남아요. i=n-1(최댓값)에서 성립하고, 매 반복 꺼낸 값은 남은 최댓값이므로 a[i] <= a[i+1]이 유지돼 i=0 종료 시 전체 정렬이 보장돼요.

  • (b)에서 child < h->heap_size 조건을 놓치고 방금 빠진 끝 칸까지 비교하면: i = 4의 두 번째 내려가기에서 child = 4일 때 heap_size = 4인데 5번 칸(옛 값 8 또는 쓰레기 값)을 읽어 heap[child+1]과 잘못 비교하게 돼요.

  • 자체 설정 및 경계 조건: 의자 5개, order=t+1, leave=t+3, “남은 의자 >= k이면 착석”은 이 문제를 위해 정한 규칙이에요(S8 p16은 “>(클 때)”만 서술했으나 이번 입력은 두 수가 같은 경우가 없어 두 해석의 답이 같아요).

이 문제를 봤을 때 떠올릴 개념과 공식

문제 단서꺼낼 도구·규칙이유와 조건
(a) 넣은 순서 vs 일어나는 시각 최소 우선순위 큐(우선순위 = 시각) vs FIFO 삽입 순서(6, 1, 8, 3)와 새로 생기는 order·leave 시각이 뒤섞여, FIFO는 시간이 역전되므로 시각이 이른 순으로 꺼내야 해요(정리노트).
(b)(c) 이벤트 규칙 3종 상태 변수 의자 = 5 추적표 arrival(t, k)는 착석/이탈 결정, order(t, k)는 t+3 leave 생성, leave(t, k)는 의자 반납을 수행해요.

종이에 쓰는 실제 첫 줄

초기 큐(시각 순 정렬): (1 arrival 3), (3 arrival 3), (6 arrival 2), (8 arrival 4) | 의자 = 5
1단계: t=1 arrival 3명 → 의자 5 >= 3 착석(남은 의자 2), (2 order 3) 삽입

왜 이렇게 푸는지 함께 따라가요

(a) 보통의 FIFO 큐가 틀리는 이유

FIFO 큐는 넣은 순서대로 꺼내므로 처음 들어온 (6, arrival, 2)를 (1, arrival, 3)보다 먼저 처리해 시간이 거꾸로 흘러요. 또 처리 중 생성되는 (2, order, 3), (5, leave, 3)이 큐 맨 뒤에 쌓여 이미 대기 중인 t=6, t=8 도착보다 늦게 실행돼요(FIFO 처리 시각 열: 6, 1, 8, 3, 7, 2, 10, 5).

실제와 달리 t=3 도착 시점에 의자가 2개가 아니라 0개로 계산되는 등 중간 인과 상태가 완전히 깨져요(이번 입력에서는 우연히 최종 나간 인원 7·남은 의자 5가 같지만 시뮬레이션으로 틀린 동작이에요). 따라서 시각이 가장 이른 이벤트를 꺼내는 최소 우선순위 큐가 필요해요.

(b) 시각 순서 이벤트 추적 (남은 의자 초기 5개)
단계꺼낸 이벤트처리 내용남은 의자처리 후 큐 (시각 순)
1(1, arrival, 3)5 ≥ 3 → 착석, (2, order, 3) 삽입2(2 order) (3 arrival) (6 arrival) (8 arrival)
2(2, order, 3)(5, leave, 3) 삽입2(3 arrival) (5 leave) (6 arrival) (8 arrival)
3(3, arrival, 3)2 < 3 → 주문 없이 나감(3명)2(5 leave) (6 arrival) (8 arrival)
4(5, leave, 3)의자 +3 반납5(6 arrival) (8 arrival)
5(6, arrival, 2)5 ≥ 2 → 착석, (7, order, 2) 삽입3(7 order) (8 arrival)
6(7, order, 2)(10, leave, 2) 삽입3(8 arrival) (10 leave)
7(8, arrival, 4)3 < 4 → 주문 없이 나감(4명)3(10 leave)
8(10, leave, 2)의자 +2 반납5빈 큐

2단계에서 새로 만든 t=5 leave가 먼저 들어 있던 t=6 arrival보다 앞서 꺼내지므로 t=6 손님이 빈 의자 5개를 만나 착석할 수 있어요.

(c) 주문 없이 나간 손님과 마지막 의자 수

주문 없이 나간 손님은 t=3의 3명과 t=8의 4명으로 총 $3 + 4 = \mathbf{7}$명이고, 마지막 leave 후 남은 의자는 5개예요.

완성 답과 검산

(a) 완성 답: 넣은 순서와 발생 시각 순서가 다르고 나중에 생긴 order·leave가 먼저 들어 있던 도착보다 먼저 일어나야 하므로, FIFO는 시간이 역전(처리 시각 6, 1, 8, 3, 7, 2, 10, 5)되어 시각 기준 최소 우선순위 큐가 필요해요.

검산: 최소 우선순위 큐의 처리 시각 열 [1, 2, 3, 5, 6, 7, 8, 10]은 단조 증가하고 동점 시각도 없지만, FIFO는 단조 증가가 깨지며 t=3 시점 의자가 0(실제 2)으로 어긋나요.

(b) 완성 답: 1 arrival(2) → 2 order(2) → 3 arrival(2, 3명 이탈) → 5 leave(5) → 6 arrival(3) → 7 order(3) → 8 arrival(3, 4명 이탈) → 10 leave(5).

검산: 모든 단계에서 의자 수가 0 ≤ 의자 ≤ 5 범위에 있고, 착석 조건 비교 (5 vs 3), (2 vs 3), (5 vs 2), (3 vs 4)에 같은 수가 없어 슬라이드의 > 해석과 문제의 >= 해석이 완전히 같은 결과를 내요.

(c) 완성 답: 나간 손님 7명, 마지막 남은 의자 5개.

검산(보존 법칙): 도착 총원 $3+3+2+4 = 12$명 = 착석 후 leave 완료 5명 + 이탈 7명, 그리고 착석한 5명 전원 반납으로 마지막 의자는 초기 5개로 복귀해요.

오해하기 쉬운 이유와 반례

  • (a)를 “FIFO로 풀면 최종 나간 손님·의자 숫자가 틀린다”로 쓰면: 이 데이터에서는 FIFO로 돌려도 우연히 마지막 숫자가 7명·5개로 같아요. 틀린 본질은 최종 우연치가 아니라 시각 순서(인과 관계)와 중간 의자 상태(t=3에 0 vs 2)가 깨진다는 점이에요.
  • (b)에서 order·leave 생성 시점을 건너뛰고 초기 도착 4개만 먼저 처리하면: t=5 leave가 실행되기 전에 t=6 arrival(2명)을 처리하게 되어 의자가 2개만 남는 잘못된 경로로 빠지고, 이때는 > vs >= 해석 차이까지 생겨 답이 어긋나요.

해설을 닫고 스스로 확인해요

  1. 이벤트 시뮬레이션 문제를 보면 → 초기 큐 목록을 시각 오름차순으로 다시 나열하고, order·leave가 생길 때마다 제 시각 자리에 끼워 넣으며 표를 채우세요.
  2. 검산할 때 → 도착 총원 = 착석 인원 + 이탈 인원과 처리 시각 열의 단조 증가 여부를 두 줄로 확인해 보세요.

떠올릴 개념·공식

이산 이벤트 시뮬레이션은 시각 기준 최소 우선순위 큐 필수(FIFO는 처리 시각 역전). 이번 입력은 >=와 > 결과 동일.

첫 줄

초기 큐 시각 순 (1,a,3)(3,a,3)(6,a,2)(8,a,4), 의자 5 → t=1 arrival 3 착석(의자 2, 2 order 삽입).

핵심 판단

1a(2)→2o(2)→3a(2,3이탈)→5l(5)→6a(3)→7o(3)→8a(3,4이탈)→10l(5). t=5 leave가 t=6 arrival보다 먼저.

검산

이탈 7명, 마지막 의자 5개(도착 12 = 착석 5 + 이탈 7). FIFO는 최종 숫자가 우연히 같으나 시각 6,1,8,3,... 역전.
