## 1. 복습: 트리 연산은 전부 재귀였다 → 이진 탐색 트리 도입 (Part 01)

**핵심 내용**

- 복습(S7 p14–17): 노드 개수를 구하거나, 수식 트리를 계산하거나, 순회할 때 모두 recursive call을 썼고 반복문은 전혀 쓰지 않았다.
- 그러므로 "트리는 전부 recursive call을 써야 되겠구나"라고 마음먹어야 한다. 재귀를 어려워하면 트리와 그래프를 프로그래밍하기는 거의 불가능하다.
- 이진 트리의 정의는 "자식 노드가 2개 이하"뿐이었다. 오늘은 binary와 tree 사이에 **search**를 넣은 binary search tree(이진 탐색 트리)를 본다.
- search의 뜻(S7 p18): 전화번호부, 사전, 일정 등에서 원하는 아이템을 탐색하는 것.

**강조 발언**

- "그래서 여러분들이 recursive call을 어려워하는 순간 트리와 그래프라고 하는 자료구조를 프로그래밍하는 건 거의 불가능합니다." (Part 01)
- "그러니까 그냥 '아, 나는 recursive call 써야지.' 이렇게 마음을 먹고 계셔야 돼요." (Part 01)

## 2. [일화] IBM 알마덴 인턴십과 구글이 빨랐던 비밀 — 서치는 "타겟을 찾는 노력" (Part 01–03)

**비유와 일화**

- 박사과정 때 논문 저자 라케시 아그라왈(Rakesh Agrawal)을 우상으로 삼아, 지도교수님께 나중에 알리고 IBM 알마덴 리서치 센터 인턴십에 한국에서 직접 지원해 합격했다. 다른 인턴은 스탠퍼드·유펜·MIT 학생이었다(Part 01).
- 당시 검색 엔진(알타비스타 등)은 화면 반이 광고였고 결과가 2~3분 걸렸다. 구글은 화면이 깨끗하고 즉시 결과가 나왔다(Part 01–02).
- **bag-of-words vs 하이퍼링크 가중치**(Part 02): 일반 검색 엔진은 문서의 명사들(교수님은 슬라이드 p18의 "전화번호부, 사전, 일정, 아이템, 탐색, 데이터, 시간, 작업"을 예로 듦)을 주머니에 담아 분야 확률을 계산해 분류한다. 예: 마이클 조던 문서라도 야구 얘기가 많으면 야구로 분류. 구글 논문은 하이퍼링크가 걸린 단어에 웨이트를 강하게 준다. 하이퍼링크는 중요해서 다는 것이기 때문이다. "소프트웨어 쪽은 그냥 내가 생각하기에 상식적으로 이랬으면 좋겠는데 그게 아이디어예요."
- **로딩 타임 역발상**(Part 02–03): 구글 연구실 출신 스탠퍼드 박사과정생이 알려 준 "트릭"은, 검색 결과의 3번째 페이지(랭킹 21~30)를 먼저 보는 사람은 없으니 확률이 강한 상위 약 10%만 먼저 로딩하고, 사용자가 첫 페이지를 보는 동안 나머지를 로드한다는 것이었다. 결과를 바로 뒤쪽 페이지로 가 보면 빈 페이지였다. 서치 알고리즘이 아니라 데이터 로딩 타임에 집중했다.
- **서치 = 타겟이 있는 행동**(Part 02): 브라우징은 할 일 없이 아무거나 보는 것이고, 서치는 목표(타겟)가 있다. 자료구조 첫 시간의 0~100 숫자 맞히기(예: 77)도 타겟을 찾는 서치였고, 순차 탐색 대신 반씩 쳐 나가는 이진 탐색으로 최악의 경우 $\log n$ 안에 찾았다.
- 검색 엔진 엔지니어 입장에서는 문서를 미리(또는 실시간으로) 분류해 두어야 한다. 이 분야를 information retrieval이라 한다(Part 02–03).
- 교훈: 연구나 디버깅이 막히면(데드락) 그 자리를 계속 고쳐 "누더기"로 만들지 말고, 한 발짝 뒤로 물러나 처음부터 다시 보라(Part 03).

## 3. 탐색 관련 용어: 레코드·필드·프라이머리 키 (Part 03–04)

**핵심 내용**

- 서치는 방대한 양의 데이터를 대상으로 하므로 시간이 많이 걸린다. 그래서 효율성을 높여야(알고리즘을 개선해야) 한다(S7 p18).
- 데이터베이스 [슬라이드 외]: 파일(CSV 등)에서 하나씩 읽어 파싱하면 I/O가 오래 걸린다. 큐를 배울 때 계산 시간과 I/O 시간 차이 때문에 버퍼(큐)가 생겼던 것과 같은 문제다. 메모리와 CPU 사이의 캐시처럼 데이터베이스 소프트웨어가 데이터를 잘 넣어 두면 빠르게 찾아 준다. SQL(시퀄)로 "소득이 1억 이상인, A로 시작하는 이름의 사람을 찾아줘" 같은 쿼리를 보낸다.
- **레코드(record)**: 하나의 행. 예: 학생 레코드(이름, 학번, 학과, 학년, GPA, 이수학점, 수강 정보…).
- **필드(field)**: 레코드 안의 낱개 항목(학번, 이름, 전화번호…).
- **프라이머리 키(primary key, 고유 키)**: 레코드를 대표할 수 있는 필드. 학생 레코드에서는 학번·전화번호가 될 수 있고, 이름은 중복될 수 있어 안 된다.

**강조 발언**

- "그러면 지금 학생 레코드에서 고유 키가 될 수 있는 건 학번, 이름은 안 됩니다. 왜? 중복일 수가 있어서 고유하지 않습니다." (Part 04)

## 4. 이진 탐색 트리의 정의 (Part 04)

**핵심 내용**

- 정의(S7 p18): 이진 트리이면서 다음을 만족한다.
  1. 모든 원소의 키는 유일하다(중복 없음).
  2. 왼쪽 서브트리의 키들은 루트의 키보다 작다.
  3. 오른쪽 서브트리의 키들은 루트의 키보다 크다.
  4. 왼쪽과 오른쪽 서브트리도 이진 탐색 트리이다(recursively defined).
- "키"는 값이라고 생각하면 된다.
- 이진 트리는 자식의 **수**만 봤지만, 이진 탐색 트리는 **값(밸류)**을 보기 시작했다.
- 크기 순서는 순회 순서로 말하면 L, V, R이다. 가장 작은 값이 왼쪽 서브트리, 중간이 루트, 큰 값이 오른쪽 서브트리에 있기 때문이다.
- S7 p19의 식 `key(왼쪽서브트리) ≤ key(루트노드) ≤ key(오른쪽서브트리)`에서 **=을 지우라**고 했다. 키가 유일하기 때문이다. 고급 자료구조에서는 중복 키를 허용하는 BST도 있어서 슬라이드에 =이 적혀 있다.

**강조 발언 / 헷갈리면 안 되는 곳**

- "자, 그래서 여기에서 =을 빼세요. 왜냐하면 유니크하다라고 했기 때문에 … 지금 여러분들은 그냥 X표 하세요. 유니크하다, 하나의 밸류만 있어야 된다 이렇게 생각을 하고요." (Part 04)
- "이제 밸류를 보기 시작했죠. 차일드의 수가 아니라." (Part 04)

## 5. 중위 순회하면 오름차순 정렬 (Part 04)

**핵심 내용**

- 예제 트리(S7 p19): 루트 18. 왼쪽 7(왼쪽 자식 3, 오른쪽 자식 12). 오른쪽 26(왼쪽 NULL, 오른쪽 31). 31의 왼쪽 자식 27.
  - 확인: 18의 왼쪽에는 18보다 큰 값이 없고, 오른쪽에는 18보다 작은 값이 없다. 7, 26, 31 기준으로도 재귀적으로 성립한다. 26의 왼쪽 서브트리처럼 비어 있으면(NULL) 그냥 만족한다.
  - 이 트리는 포화 이진 트리도, 완전 이진 트리도 아닌 "기타 이진 트리"다.
- **중위 순회(LVR) 추적**
  1. 18: "스택아 너 저장해, 나 L로 내려간다" → 7 → 다시 L로 → 3.
  2. 3의 L은 없어서 튕겨 나오며 V: **3**. R도 없다.
  3. 7의 L이 끝났으니 V: **7**. R로 내려가 12의 L(없음) 후 V: **12**.
  4. 18의 L이 끝났으니 V: **18**. R로 내려간다.
  5. 26의 L은 없으니 V: **26**. R로 내려가 31 서브트리의 L부터: **27**, V: **31**.
  - 결과: 3, 7, 12, 18, 26, 27, 31. "저절로 오름차순으로 소팅 되어 있습니다."
- 그림에서 NULL 확인을 생략했다고 해서 안 들어간 것은 아니다. 바닥 조건(NULL)은 계속 쳐야 한다.
- "그냥 스택이나 큐에 넣고 크기 비교해서 정렬하면 안 되나?"라는 물음(교수님 자문)에 대한 답: 트리를 쓰면 최악의 경우는 순차와 같지만 **높이에 비례하는** 알고리즘을 얻는다. 그것이 장점이라서 트리를 써야 한다.
- 트리와 힙이 끝나면 정렬(sorting) 챕터에서 여러 자료구조를 이용한 정렬을 본다.

**비유와 일화**

- **개발자의 원칙 — 책상 서랍**: "복잡한 건 누구 몫? 개발자 몫. 편리한 건 누구 몫? 사용자 몫." 내 책상이면 아무렇게나 넣고 찾는 데 시간을 써도 되지만, 개발자는 책상 주인(사용자)이 가장 빨리 찾을 수 있도록 서랍을 정리해 두는 사람이다. 그래서 번거로워도 BST로 만들어 둔다(Part 04).

**강조 발언**

- "자, 이제 밑에 널인 거 안 할게요. 어 안 한다고 해서 안 들어간 건 아닙니다, 바닥 조건은 계속 쳐야 돼요. 제가 이거 계속 강조하고 있습니다." (Part 04)
- "어쨌든 트리라고 하는 걸 가져가는 순간 뭐가 된다? 최악의 경우는 시퀀셜이랑 똑같지만 높이에 비례하는 알고리즘을 얻을 수 있다." (Part 04)
- "개발자는 무조건 사용자의 편의를 위해서 코딩 해야 되는 사람들이에요." (Part 04)

**학생과의 대화**

- 실제 학생 발언은 없다. "이거 그냥 크기 비교하면 안 돼요? … 소팅 하면 안 돼요?"는 교수님의 자문자답이다(Part 04). 이 수업 전체에서 학생 발언으로 확인되는 대목은 없다(Part 02 끝 "0번부터, 1번부터"도 교수님이 이어 말한 것으로 보인다).

🕳️ 미룬 유도: 다른 자료구조를 이용한 정렬은 "트리하고 힙하고 끝나면 소팅이라고 하는 챕터"에서 본다(Part 04).

## 6. 탐색 연산 (Part 04–05)

**핵심 내용**

- 규칙(S7 p20)
  - 비교 결과가 같으면 탐색 성공으로 끝난다(순차 자료구조에서도 같다).
  - 찾는 키가 루트 키보다 작으면 왼쪽 자식을 기준으로 다시(재귀적으로) 시작한다.
  - 크면 오른쪽 자식을 기준으로 다시 시작한다.
- **성공 예: 12 찾기**(예제 트리)
  1. "너 12니?" 18 → 아니다. 12 < 18이므로 왼쪽으로. 오른쪽 서브트리는 후보 셋에서 사라진다.
  2. 7 → 아니다. 12 > 7이므로 오른쪽으로.
  3. 12 → 찾았다. 비교 3번.
  - 배열 표현법 인덱스로는 5번(18=1, 7=2, 26=3, 3=4, 12=5)을 반환한다.
  - 트리 높이는 4(18→26→31→27)인데 비교는 3번이었다. 높이만큼 비교하는 것은 **최악의 경우**다.
  - 순차 탐색이라면: 정렬돼 있으면 우연히 3번(3, 7, 12), 무작위면 최악 $n = 7$번.
- **실패 예: 20 찾기**: 18보다 크니 오른쪽 26 → 20 < 26이라 왼쪽으로 가니 NULL. 두 번 만에 NULL을 반환한다. "없어도 없다는 걸 알려 줍니다."
- **슬라이드 코드**(S7 p20)

```c
Typedef struct TreeNode {
int key;
struct TreeNode *left, *right;
} TreeNode;
```

```c
search(x, k)
if x=NULL
then return NULL;
if k=x->key
then return x;
else if k<x->key
then return search(x->left, k);
else return search(x->right, k);
```

  - 슬라이드에는 C 시그니처 `TreeNode *search(TreeNode *node, int key)`도 적혀 있다.
  - x는 트리(루트)를 가리키고 k는 찾을 값이다. x가 NULL이면 "아무것도 없어", 같으면 x 자체를 반환, 작으면 왼쪽·크면 오른쪽으로 search를 재귀 호출한다.
- 반복문으로 짜면 "되게 지저분해지"므로 재귀로 구현한다는 것이 교수님 설명이다. [보충] 다음 쪽의 insert_node 의사코드는 while 반복문으로 되어 있다.
- 시간복잡도: 최악의 경우 높이만큼 비교 → $O(h)$(분석은 9절).

**강조 발언**

- "바이너리 서치 트리는 왼쪽 서브트리가 작다는 걸 보장하고 있어요. … 오른쪽은 갑자기 후보 셋에서 사라집니다." (Part 05)
- "네, 최악의 경우 높이만큼 비교를 합니다." (Part 05)

## 7. 삽입 연산 (Part 05)

**핵심 내용**

- 자료구조의 단골 연산: traversal, insert, delete.
- 일반 이진 트리라면 완전 이진 트리 순서상 다음 자리에 넣겠지만, BST는 "left < 루트 < right"를 유지해야 하므로 들어갈 **자리를 찾아서** 넣어야 한다.
- 삽입은 **먼저 탐색**한다(S7 p21). 키가 유일해야 하므로 이미 있으면 삽입하지 않는다. **탐색에 실패한 위치가 바로 새 노드가 들어갈 자리**다.
- **예: 9 삽입**: 18보다 작아 왼쪽 → 7보다 커 오른쪽 → 12보다 작아 왼쪽 → NULL. "9 없어. 너 insert 가능해." 그 자리(12의 왼쪽 자식)에 넣는다. 배열이면 인덱스가, 연결 리스트면 포인터가 그 위치를 알려 준다.
- **슬라이드 코드**(S7 p21)

```c
insert_node(T,z)
p←NULL;
t←root;
while t≠NULL do
// 빈자리찾기
{
if (z->key = t->key) return;
p←t;
if z->key < p->key
then t←p->left;
else t←p->right;
}
if p=NULL
then root←z;// 트리가비어있음
else if z->key < p->key // insert
then p->left←z
else p->right←z
```

  - 슬라이드 설명: "Tree T에서 z에 대한 탐색".
  - t는 루트에서 시작해 서브트리의 루트를 쫓아 내려가는 포인터, p는 t를 바로 뒤따르는 부모 포인터다.
  - 키가 같으면 그냥 return(삽입 안 함). 작으면 left, 크면 right로 내려간다.
  - 루프가 끝나면 p가 새 노드의 부모다. p가 NULL이면 트리가 비어 있던 것이므로 z가 root가 된다. 아니면 키 크기에 따라 p의 왼쪽 또는 오른쪽 자식으로 붙인다.
- 정리: 삽입 = 탐색 + 반환된 포인터에서 작으면 왼쪽, 크면 오른쪽에 붙이기. 시간복잡도는 탐색과 같이 $O(h)$.

**비유와 일화**

- 책상 서랍에 물건을 "팍" 넣고 닫을 수 없는 자료구조다. 9가 들어갈 위치를 찾아서 넣어야 한다(Part 05).

**강조 발언**

- "살짝 순차가 아니라서 걱정이 되겠지만 걱정할 거 하나도 없어요. 엄청 쉬워요." (Part 05)
- "왜? 유니크(unique)해야 된다 그랬잖아요. 있으면 insert 안 하는 겁니다." (Part 05)
- "좋죠? 서치를 하는 순간 내가 들어가야 될 자리를 만들어 주는 거예요." (Part 05)

## 8. 삭제 연산: 세 가지 경우 (Part 05–06)

**핵심 내용**

- 삭제는 삽입보다 까다롭다. 세 경우 모두, 이어 붙인 뒤에도 **BST 조건을 계속 만족**해야 한다(S7 p22).
- **CASE 1: 단말(leaf) 노드 삭제**(S7 p22): 부모 노드를 찾아 연결을 끊으면 된다.
  - 배열 표현이면 그 칸만 비운다. 링크 표현이면 부모의 해당 자식 포인터를 NULL로 만든다.
  - 나머지는 달라진 것이 없으므로 여전히 BST다.
- **CASE 2: 서브트리를 하나만 가진 노드 삭제**(S7 p23): 노드는 삭제하고 서브트리를 부모 노드에 붙인다("이어 붙이기").
  - 예: 오른쪽 자식을 단 68을 삭제. 그냥 자르면 자식까지 덩달아 사라진다(데이터 손실).
  - 링크 표현이면 부모가 68을 가리키던 포인터를 68의 자식을 가리키게 바꾼다. 교수님은 배열이면 "parent 노드의 인덱스로 변경"한다고 했다.
  - 이어 붙여도 부모(35)보다 큰 값이 여전히 오른쪽에 있으므로 BST가 유지된다. "어떤 경우에도 얘는 상관이 없습니다."
- **CASE 3: 서브트리를 두 개 가진 노드 삭제**(S7 p24): 삭제 노드와 가장 비슷한 값을 가진 노드를 삭제 노드 위치로 가져온다.
  - 문제: 예제 트리에서 7(자식 3, 12)을 그냥 잘라 이어 붙이면 18의 자식이 3, 12, 26으로 셋이 되어 이진 트리가 아니다.
  - 해결: 왼쪽 서브트리에서 **가장 큰** 값, 또는 오른쪽 서브트리에서 **가장 작은** 값을 올린다. 슬라이드 그림 예에서는 왼쪽 후보가 12, 오른쪽 후보가 22이고, 책에서는 22를 올렸다.
  - 교수님 설명: 일반적으로 왼쪽 서브트리의 값을 올리지만, 오른쪽의 가장 작은 값을 올려도 상관없다. 선택하기 나름이다.
  - 올린 뒤 확인: 나머지는 그대로이므로 올라간 자리만 보면 된다. 22보다 작은 값은 왼쪽, 큰 값은 오른쪽에 모여 있어 만족한다.
- 이번 수업에서 삭제 C 코드나 의사코드는 보지 않았다(슬라이드 p22–24에도 코드 없음). 시간복잡도는 9절에서 $O(h)$로 묶었다.

**비유와 일화**

- **가지치기**: 리프는 가위로 그 가지만 "똑" 자르면 끝이다(Part 05).
- **조폭 두목 승계**: A 그룹과 B 그룹을 거느린 두목이 죽으면, A에서 제일 힘센 사람이나 B에서 제일 힘센 사람이 올라가 평정하면 된다. BST에서 "힘세다"는 값의 크기 자체가 아니라 **순서 조건**(왼쪽 < 루트 < 오른쪽)을 지킬 자격이다. 왼쪽에서는 가장 큰 값, 오른쪽에서는 가장 작은 값이 그 자격을 가진다(Part 06). (그 전에 "큰집 작은집, 할아버지가 돌아가셨다"로 시작했다가 조폭 비유로 바꿨다.)

**강조 발언 / 헷갈리면 안 되는 곳**

- "근데 안 돼요. 소프트웨어에서 제일 싫어하는 게 데이터 손실입니다. 데이터를 손실시키면 안 돼요, 소프트웨어는 절대로." (Part 05)
- "이 세 가지 경우 모두 뭐를 고려해야 되냐면 이어붙이기를 하더라도 binary search tree를 계속해서 만족시키는 트리여야 된다는 거예요." (Part 06)
- "밸류가 크다 작다가 중요한 게 아니라 그 순서를 지켜야 되는 게 대원칙입니다." (Part 06)
- "루트보다 left subtree가 작고, right subtree가 크다. 그게 대원칙이에요. 그것만 지키면 되거든요, binary search tree는." (Part 06)

## 9. [일화] 현대자동차 철가방과 병풍 캐스케이딩, 신호를 이미지로 (Part 06–07)

**비유와 일화**

- 소프트웨어는 평범한 사람도 아이디어로 성능 개선을 보일 여지가 많다는 이야기로 꺼냈다(삭제 CASE 3의 "기가 막힌" 아이디어에서 이어짐).
- 현대자동차 연구 과제에서 100ms마다 100개 데이터가 필요했는데, 받은 것은 열 수 없는 "철가방"(시리얼 포트만 노출, 몇 초에 10개)이었다. 차량용 보드는 생명과 관련돼 CPU 사용률조차 바꿀 수 없었다.
- "소프트웨어로는 안 되는 게 없다"는 철칙으로, 같은 테스트 코드를 10번 돌려 매번 다른 10분의 1 조각을 얻고, 병풍처럼 캐스케이딩해 펼쳐 1초에 10개를 100개 상태로 전처리했다. 논문 서론은 도마뱀 사진을 조금씩 보여 주는 예로 썼고 바로 억셉됐다.
- 신호 고장 진단(fault detection)에서 값으로 바꿔 딥러닝에 넣으니 80%에 그쳤는데, 오실로스코프처럼 파형을 이미지로 넣었더니 성능이 좋아졌다.
- 교훈: 드릴다운만 하지 말고 한 발짝 뒤에서 상식 수준의 해법을 고민하라. "프로그래밍은 어디까지나 아이디어와 프랙티스입니다. 사실 띠어리(theory)가 아니에요."

**강조 발언**

- "'교수님 수업 시간에 설명할 때는 되게 쉬운데 코딩을 하면 어렵고, 시험 문제에 코딩 문제가 나오면 어렵다.' 이렇게 얘기를 하거든요. 컨셉 자체는 어렵지가 않아요." (Part 07) — 강의 평가 주관식을 인용하며, 농구 비유("직접 해 보세요, 되나")로 직접 코딩해 보는 연습을 강조했다.

## 10. 이진 탐색 트리의 분석 (Part 07)

**핵심 내용**

- 탐색·삽입·삭제 모두 높이만큼 따라 내려가므로 시간복잡도는 트리 높이 $h$에 비례한다: $O(h)$(S7 p25).
- 하지만 $O(h)$로 끝내면 안 되고 $n$의 함수로 표현해야 한다.
- **최선의 경우**: 이진 트리가 균형적으로 생성된 경우 $h = \log_2 n$, 따라서 $O(\log_2 n)$. 포화·완전 이진 트리가 여기 해당한다(높이는 대략 $\log_2(n+1)$이지만 $\log n$으로 본다).
- **최악의 경우**: 한쪽으로 치우친 경사 이진 트리(skewed). 예: 1 → 2 → 3 → 4가 계속 오른쪽 자식으로 이어진 트리. 이것도 이진 트리이자 이진 탐색 트리다. 노드 4개에 높이 4, 즉 $h = n$이고 $O(n)$이라 순차 탐색과 같다.
- 그래도 트리를 쓴다 [슬라이드 외]
  - 실제로 이렇게 치우치는 경우는 드물고, 그렇다고 평균적으로 완전히 예쁘게 만들어지지도 않는다. 대부분 "저 정도"의 중간 모양이라 순차보다 낫다.
  - 그래서 트리에 한해서는 최악의 경우로 이야기하지 않는다.
  - 최악으로 가고 있으면 최악이 안 되게 만드는 알고리즘을 백그라운드에서 돌리면 된다.
- **AVL 트리**(S7 p25): Adelson-Velsky와 Landis가 만들었다. balance factor로 스스로 높이를 균형 있게 재배치한다.
- 그 밖의 트리: 2-3 tree, 2-3-4 tree, B-tree, B+-tree. 거의 다 이진 트리를 기본으로 하고 거기에 제약 조건을 하나 더 붙여 특정 작업에 최적화한 것이다. 겁먹지 말고 "정의가 뭐지?"로 접근하라.

**강조 발언 / 헷갈리면 안 되는 곳**

- "그래서 O(h)라고 할 수 있는데, 어 이거 n의 함수로 표현해야지 이렇게 하면 안 되죠. 그렇죠?" (Part 07)
- "그러니까 얘는 어떠냐면 h는 n이 돼서요, O(n)이 돼서 트리를 기껏 만들었지만 순차 탐색과 시간 복잡도가 똑같아집니다." (Part 07)
- "그래서 최악의 경우가 이렇긴 하지만 최선의 경우가 로그 n이기는 하지만 우리는 이거를 최악의 경우로 얘기하지 않는다, 트리에 한해서." (Part 07)

🕳️ 미룬 유도: 트리 모양이 평균적으로 어떻게 되는지는 "그런 거는 힙(heap)에 가서 더 자세히 보긴 할 거예요"(Part 07).
🕳️ 미룬 유도: AVL과 balance factor는 "우리 맨 마지막 챕터가 서치(search)거든요. 거기에서 다시 한번 설명을 할 거고요"(Part 07).
🕳️ 미룬 유도: 2-3, 2-3-4, B, B+ 트리 등은 고급 자료구조(소프트웨어학과 대학원 수업)에서 배울 수 있다고만 했다(Part 07–08).

- AVL 트리 (Adelson-Velsky and Landis), balance factor, 2-3 tree, 2-3-4 tree, B-tree, B+-tree
- (일화 속) bag-of-words, 하이퍼링크 가중치(weight), information retrieval, 캐스케이딩 (cascading), fault detection

**코드 (슬라이드 글자 그대로)**

- `Typedef struct TreeNode { int key; struct TreeNode *left, *right; } TreeNode;` (S7 p20)
- `TreeNode *search(TreeNode *node, int key)` (S7 p20)
- `search(x, k)` / `if x=NULL then return NULL;` / `if k=x->key then return x;` / `else if k<x->key then return search(x->left, k);` / `else return search(x->right, k);` (S7 p20)
- `insert_node(T,z)` / `p←NULL;` / `t←root;` / `while t≠NULL do` / `if (z->key = t->key) return;` / `p←t;` / `then t←p->left;` / `else t←p->right;` / `if p=NULL then root←z;// 트리가비어있음` / `then p->left←z` / `else p->right←z` (S7 p21)

## 시험·과제 언급

- "'교수님 수업 시간에 설명할 때는 되게 쉬운데 코딩을 하면 어렵고, 시험 문제에 코딩 문제가 나오면 어렵다.' 이렇게 얘기를 하거든요." (Part 07)
  - 강의 평가 주관식에 나온 학생 의견을 인용한 것이다. 시험에 코딩 문제가 나온다는 전제는 있으나, 앞으로의 시험 범위·출제에 대한 구체적 안내는 아니다.
- "과제"라는 말은 모두 교수님 연구실의 현대자동차 산학 과제(Part 06–07) 이야기이며 수업 과제가 아니다.
- 시험 범위, 수업 과제, 실습에 대한 언급은 없다.
